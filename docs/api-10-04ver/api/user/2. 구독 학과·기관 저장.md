# 구독 학과·기관 저장

**구독할 학과·기관을 저장합니다. 온보딩 2단계의 "다음" 버튼과 마이페이지 구독 관리의 "저장" 버튼이 같은 API 를 부릅니다. 개별 추가·삭제가 아니라 **최종 선택 집합 전체**를 보내면 서버가 현재 상태와 비교해 차이만 반영하고, 저장 후의 목록을 그대로 돌려줍니다.**

- **Method / Endpoint: `PUT /api/v1/users/me/vendors`**
- **Auth Required: Required (User)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |
| Content-Type | application/json | | **필수** |

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| ids | Array&lt;Long&gt; | 구독할 `vendors.id` 의 **최종 목록**. 체크박스 상태를 그대로 보내면 됩니다 | **필수** |

> **`ids` 는 델타가 아니라 전체 교체 목록입니다.** 빠진 id 는 구독 해제로 처리됩니다.
> 하나를 추가하려고 그 id 만 보내면 나머지 구독이 전부 사라집니다.

> **`SCHOOL` 유형만 넣을 수 있습니다.** 동아리(`CLUB`) 제공처 id 를 섞어 보내면
> `400 INVALID_VENDOR_TYPE` 으로 요청 전체가 실패합니다. 동아리 관심은
> `PUT /users/me/interests/club-types` 로 다룹니다. 구판 명세가 이 목록을 "학과·기관·동아리" 라고
> 적고 있었지만 실제로는 DB 트리거가 `SCHOOL` 이외를 막습니다.

> **빈 배열 `[]` 은 온보딩 중에만 거부됩니다.** 온보딩을 마친 뒤에는 "전부 해제" 로 정상
> 처리됩니다 — 설정 화면에서 마지막 하나를 끄는 것을 막을 이유가 없기 때문입니다.
> 온보딩 여부는 클라이언트가 알려주는 값이 아니라 **서버가 DB 의 온보딩 완료 시각으로 판정**합니다.

> **`ids` 필드 자체를 빼면 `400 INVALID_INPUT_VALUE`** 입니다. `[]` 와 필드 누락은 다릅니다.

> **중복 id 는 한 번으로 합쳐집니다.** 요청은 집합으로 다뤄지므로 `[3, 3, 7]` 은 `[3, 7]` 과 같습니다.

## Request Sample

```json
PUT /api/v1/users/me/vendors
Authorization: Bearer eyJ...
Content-Type: application/json

{
  "ids": [3, 7]
}
```

전부 해제 (온보딩 완료 후에만 허용):

```json
{
  "ids": []
}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Array | 저장 후의 목록. `GET /users/me/vendors` 와 완전히 같은 모양 |
| data[].id | Long | `vendors.id` |
| data[].name | String | 제공처 이름 |
| error | Object | 에러 정보 (성공 시 키 자체가 빠짐) |

> **응답이 GET 과 동일합니다.** 저장 직후 GET 을 다시 부르지 마세요. 서버가 실제로 무엇을
> 저장했는지가 이 응답에 그대로 드러납니다.

> 정렬은 **이름 오름차순**입니다. 요청에 보낸 배열 순서는 보존되지 않습니다.

## Response Sample

```json
{
  "success": true,
  "data": [
    { "id": 7, "name": "교무처" },
    { "id": 3, "name": "소프트웨어학과" }
  ]
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | ids: ids 는 필수입니다. | `ids` 필드가 없거나 `null` |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | 본문이 없거나 JSON 이 아님, `ids` 원소가 숫자가 아님 |
| 400 | ONBOARDING_MIN_SELECTION | 최소 1개 이상 선택해야 합니다. | **온보딩 중**에 `ids: []` 를 보낸 경우 |
| 400 | INVALID_VENDOR_TYPE | 구독 대상은 학과·기관(SCHOOL)만 가능합니다 (vendor_id=12, type=CLUB) | `CLUB` 유형 제공처를 구독하려 한 경우 (DB 트리거 `IN006`) |
| 400 | RELATED_RESOURCE_NOT_FOUND | 참조 대상이 존재하지 않습니다. | 존재하지 않는 `vendor_id` (FK 위반). **조용히 무시하지 않습니다** |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료·무효화됨 |
| 404 | USER_NOT_FOUND | 존재하지 않는 사용자입니다. | 계정이 없거나 이미 `WITHDRAWN` |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> **`INVALID_VENDOR_TYPE` 의 `message` 는 ErrorCode 기본 문구가 아니라 DB 트리거가 만든
> 문장입니다.** 문제가 된 `vendor_id` 와 실제 `type` 이 괄호 안에 들어 있어 그대로 노출해도
> 쓸 만합니다. 반대로 `RELATED_RESOURCE_NOT_FOUND` 같은 표준 제약 위반은 PostgreSQL 이 만든
> 영문 메시지 대신 기본 문구가 내려갑니다(제약 이름이 노출되지 않도록).

> **부분 성공이 없습니다.** 목록에 잘못된 id 가 하나라도 있으면 트랜잭션 전체가 롤백되어
> 아무것도 저장되지 않습니다. 벌크 API 들과 달리 `data.failed` 같은 구조가 없습니다.
