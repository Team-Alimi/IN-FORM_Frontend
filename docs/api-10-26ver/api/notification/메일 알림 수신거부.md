# 메일 알림 수신거부

**알림 메일 하단의 링크입니다. 로그인 없이 메일 수신을 끕니다. 브라우저에서 열리는 화면이라 JSON 이 아니라 HTML 을 돌려줍니다.**

- **Method / Endpoint: `GET /api/v1/notifications/email/unsubscribe` — 확인 페이지**
- **Method / Endpoint: `POST /api/v1/notifications/email/unsubscribe` — 실제 해제**
- **Auth Required: Not Required**

> ## ★ 프론트가 구현할 것은 없습니다
>
> 이 두 경로는 **백엔드가 HTML 을 직접 그립니다.** 메일 본문의 링크를 사용자가 누르면
> 브라우저가 바로 이 주소를 열고, 거기서 끝납니다. 프론트 라우트도, 화면도 필요하지 않습니다.
>
> 명세에 올려 둔 이유는 두 가지입니다 — ① 이런 경로가 존재한다는 사실,
> ② **`00-common.md` 의 응답 봉투를 따르지 않는 유일한 엔드포인트**라는 점.

> ## ★ 응답 봉투(`{"success": ..., "data": ...}`)를 쓰지 않습니다
>
> `Content-Type: text/html; charset=UTF-8` 이고 본문은 사람이 읽는 페이지입니다.
> 이 주소를 여는 것은 API 클라이언트가 아니라 **브라우저**입니다 —
> `ApiResponse` 를 돌려주면 사용자가 원시 JSON 을 보게 됩니다.

# ★ GET 과 POST 로 쪼갠 이유

**한 번의 `GET` 으로 수신을 끄면 안 됩니다.**

Gmail · Outlook 같은 메일 클라이언트와 회사 메일 게이트웨이의 링크 검사기는
**사용자가 누르지 않아도** 본문의 링크를 미리 받아 봅니다(prefetch).
`GET` 에서 상태를 바꾸면 **메일이 도착한 것만으로 알림이 꺼집니다.**
사용자는 자기가 끈 적도 없는데 알림이 안 온다고 느끼고, 원인은 어디에도 남지 않습니다.

| Method | 하는 일 | 상태 변경 |
|---|---|---|
| `GET` | 버튼이 있는 확인 페이지를 그립니다 | **없음** |
| `POST` | 메일 수신을 끕니다 | 있음 |

확인 페이지의 버튼이 같은 경로로 `POST` 합니다. 프리페치는 `GET` 만 하므로 아무 일도 안 납니다.

> 이 분리가 없다는 이유로 과거에 수신거부 링크 자체를 포기했던 적이 있습니다
> (`user/5. 알림 수신 설정 변경.md` 의 옛 메모). 분리하면 성립합니다.

# Request

## Query Param (GET) / Body Param (POST)

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| token | String | 메일 링크에 담긴 서명 토큰 | **필수** |

`POST` 는 `application/x-www-form-urlencoded` 본문으로 받습니다(쿼리스트링도 받습니다).

## Request Sample

```
GET /api/v1/notifications/email/unsubscribe?token=7.1793404800.kK9r_h2Nq...
```

```
POST /api/v1/notifications/email/unsubscribe
Content-Type: application/x-www-form-urlencoded

token=7.1793404800.kK9r_h2Nq...
```

# ★ 토큰

```
<userId>.<만료 epoch 초>.<base64url(HMAC-SHA256)>
```

| | |
|---|---|
| 서명 | HMAC-SHA256. 키는 `UNSUBSCRIBE_SECRET` |
| 유효 기간 | 90일 |
| 담는 것 | **사용자 id**. 이메일 주소는 담지 않습니다 |

- **JWT 가 아닙니다.** 인증 토큰과 모양이 같으면 수신거부 토큰을 `Authorization` 헤더에
  넣어 보는 시도가 가능해집니다. 형식이 다르면 인증 필터가 파싱조차 못 합니다.
- **키가 `JWT_SECRET` 과 분리돼 있습니다.** 같은 키를 쓰면 수신거부 토큰 하나가 새어 나갔을 때
  인증 서명과 같은 비밀을 쓰는 셈이 되고, 키를 돌려야 할 때 **전원 로그아웃**이 따라옵니다.
- **주소를 담지 않는 이유** — 링크 자체가 개인정보가 되면 메일 전달·브라우저 히스토리·
  웹서버 접근 로그에 주소가 그대로 남습니다.
- **만료가 서명에 포함됩니다.** 만료 숫자만 먼 미래로 바꿔 붙이면 서명이 안 맞아 거부됩니다.
- 유효 기간을 90일로 둔 이유 — 알림 자체가 30일 뒤 삭제되므로(SYS-04) 실제로 만료된 링크를
  누를 일이 드물고, 무기한으로 두면 한 번 새어 나간 링크가 영구 버튼이 됩니다.

# Response

| HTTP Status | 페이지 | 언제 |
|---|---|---|
| 200 | 확인 페이지 (`GET`) | 토큰이 유효함 |
| 200 | 완료 페이지 (`POST`) | 수신거부 처리됨 |
| 400 | 안내 페이지 | 토큰이 없거나 만료·위조·형식 오류 |

## ★ 실패 이유를 구분해 보여주지 않습니다

만료와 위조를 나눠 알려 주면 토큰을 바꿔 가며 찔러 보는 쪽에
"형식은 맞다 / 서명은 맞다" 를 알려 주게 됩니다. 어느 경우든 사용자가 할 일은 하나입니다 —
**설정 화면에서 끄는 것.** 그래서 문구가 하나입니다.

## ★ 성공과 "이미 그런 상태" 를 구분하지 않습니다

이미 꺼 둔 사용자, 탈퇴한 사용자, 방금 끈 사용자 — 셋 다 200 완료 페이지입니다.
세 경우 모두 "메일 알림을 받지 않습니다" 가 사실이고,
구분해서 응답하면 **토큰으로 계정 존재 여부와 탈퇴 상태를 떠볼 수 있게 됩니다.**

# 끄는 방향으로만 동작합니다

이 링크로는 **다시 켤 수 없습니다.** 켜는 것은 로그인이 필요한
`PATCH /api/v1/users/me` (`user/5. 알림 수신 설정 변경.md`) 뿐입니다.
서명 토큰 하나로 수신을 켤 수 있으면, 토큰이 새어 나갔을 때
사용자가 끈 설정을 남이 되돌릴 수 있게 됩니다.

# 인앱 알림은 그대로입니다

수신거부는 **메일만** 끕니다. `GET /api/v1/notifications` 목록과
안 읽은 개수 배지는 영향을 받지 않습니다. 완료 페이지에도 그렇게 적혀 있습니다.

# UNSUBSCRIBE_SECRET 이 없으면

서명기가 비활성이 되고 **메일 본문에서 수신거부 문단이 빠집니다.**
누를 수 없는 링크를 적어 두는 것보다 없는 편이 낫다는 판단입니다.
그 상태에서도 설정 화면에서는 끌 수 있으므로 수신거부 수단 자체가 사라지는 것은 아닙니다.

이 경로로 들어온 요청은 모두 400 입니다.
