# 토큰 재발급

**Refresh Token 으로 새 Access Token 을 받습니다. Access Token 이 만료돼 401 을 받은 시점에 프론트가 조용히 호출하고, 성공하면 원래 요청을 재시도합니다. Rotation 방식이라 응답에는 새 Refresh Token 도 함께 들어 있고, 요청에 쓴 Refresh Token 은 그 즉시 폐기됩니다.**

- **Method / Endpoint: `POST /api/v1/auth/token/refresh`**
- **Auth Required: Not Required**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Content-Type | application/json | | **필수** |

> **`Authorization` 헤더가 필요 없습니다.** 이 API 는 Access Token 이 이미 만료된 상태에서
> 불리므로 로그인 상태를 요구할 수 없습니다. 보내도 무시됩니다 — 대상 세션은 오직
> 본문의 `refresh_token` 이 지목합니다.

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| refresh_token | String | 로그인 또는 직전 재발급에서 받은 Refresh Token | **필수** |

### Rotation 과 재사용 탐지

1. 서명·만료를 검증하고, Redis 에 그 세션이 **살아 있는지** 확인합니다.
   서명이 유효해도 서버 기록이 없으면 무효입니다 — 로그아웃·강제 무효화가 서버 측에서
   가능해야 하기 때문입니다.
2. 옛 토큰을 **소비 처리**하고 새 토큰을 발급합니다.
3. 소비 처리된 토큰이 다시 오면 **탈취로 간주해 해당 사용자의 전체 세션을 끊습니다.**

> **★ 응답의 `refresh_token` 을 반드시 덮어써 저장하세요.** 옛 값을 그대로 두고 다시 보내면
> 재사용으로 탐지돼 **모든 기기가 로그아웃됩니다.** 공격자가 훔친 토큰을 쓰는 순간
> 정상 사용자도 함께 끊기는 설계이며, 세션이 조용히 유지되는 것보다 낫다고 판단한 결과입니다.
>
> 그래서 **재발급 요청은 동시에 두 번 보내면 안 됩니다.** 여러 요청이 401 을 받고 각자
> 재발급을 부르면 뒤늦은 쪽이 이미 소비된 토큰을 보내게 되어 전체 세션이 끊깁니다.
> 프론트는 재발급을 한 개의 요청으로 묶어(single-flight) 처리해야 합니다.

> **권한 변경은 이 경로로 반영됩니다.** 서버가 DB 에서 `role` 을 다시 읽어
> 새 Access Token 에 담습니다. 관리자에서 강등된 계정은 Access Token 만 끊기고
> Refresh Token 은 남으므로, 한 번 401 을 받고 여기서 새 권한을 받아 갑니다.

## Request Sample

```json
POST /api/v1/auth/token/refresh
Content-Type: application/json

{
  "refresh_token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI3IiwianRpIjoiM2Y4Yi..."
}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.access_token | String | 새 Access Token. **유효기간 1시간** |
| data.refresh_token | String | **새 Refresh Token. 옛 값은 이미 폐기됐습니다** (유효기간 14일) |
| data.user_info | Object | 사용자 정보 |
| data.user_info.user_id | Long | 사용자 고유 ID |
| data.user_info.email | String | 이메일 (소문자) |
| data.user_info.name | String | 이름 |
| data.user_info.role | String | `USER` \| `ADMIN`. DB 를 다시 읽은 **현재** 권한 |
| data.user_info.onboarding_completed | Boolean | 온보딩 완료 여부 |
| error | Object | 에러 정보. **성공 응답에는 이 키가 아예 없습니다** |

> **응답 모양이 구글 로그인과 완전히 같습니다.** 프론트는 로그인과 재발급에 같은 처리 코드를 쓰면 됩니다.
>
> `user_info` 는 매번 DB 에서 다시 읽은 **현재** 값입니다. 그래서 앱을 오래 켜 둔 사용자도
> 재발급 시점에 권한 변경이나 온보딩 상태가 자동으로 따라옵니다 —
> 클라이언트가 캐시해 둔 프로필을 이 값으로 덮어쓰면 됩니다.

## Response Sample

```json
{
  "success": true,
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI3Iiwicm9sZSI6IlVTRVIifQ...",
    "refresh_token": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiI3IiwianRpIjoiYTkxYy...",

    }

```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | refreshToken: refresh_token 은 필수입니다. | `refresh_token` 이 없거나 공백. **필드명이 camelCase(`refreshToken`)** 로 나갑니다 |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | 본문이 비었거나 JSON 으로 파싱되지 않음 |
| 401 | TOKEN_EXPIRED | 만료된 토큰입니다. | Refresh Token 의 14일이 지남. **코드가 `INVALID_REFRESH_TOKEN` 이 아닙니다** |
| 401 | INVALID_REFRESH_TOKEN | 유효하지 않은 리프레시 토큰입니다. | 서명 위조·형식 오류 / `jti` 가 없음(= Access Token 을 이 자리에 보냄) / 로그아웃됐거나 서버에 세션 기록이 없음 |
| 401 | INVALID_REFRESH_TOKEN | 세션이 만료되었습니다. 다시 로그인해 주세요. | **재사용 탐지 — 이 시점에 전체 세션이 폐기됩니다.** 권한 변경과 재발급이 같은 순간에 겹친 경우도 같은 응답입니다 |
| 404 | USER_NOT_FOUND | 존재하지 않는 사용자입니다. | 탈퇴했거나 존재하지 않는 사용자. **401 이 아니라 404 입니다** |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류. 세션 저장소(Redis) 장애도 여기로 나갑니다 |

> **`세션이 만료되었습니다. 다시 로그인해 주세요.` 를 받으면 재시도하지 말고 로그인 화면으로 보내세요.**
> 이 응답이 나갈 때 요청에 쓴 토큰은 이미 소비 처리된 뒤입니다. 같은 값으로 다시 시도하면
> 재사용으로 탐지돼 상황이 더 나빠집니다.
>
> 두 갈래 모두 코드가 `INVALID_REFRESH_TOKEN` 이라 **메시지로만 구분됩니다.** 다만 프론트의
> 대응(재로그인)은 어느 쪽이든 같으므로 코드만 보고 처리해도 무방합니다.

> **재발급 실패는 401 과 404 두 계열로 나옵니다.** 탈퇴한 계정으로 재발급을 시도하면 404 이므로,
> "재로그인 유도" 분기를 401 에만 걸어 두면 탈퇴 계정이 무한 재시도에 빠집니다.
