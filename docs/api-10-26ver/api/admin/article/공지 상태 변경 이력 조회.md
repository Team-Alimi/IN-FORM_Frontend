# 공지 상태 변경 이력 조회

**공지 한 건의 상태가 언제·누가·왜 바뀌었는지 전체 이력을 최신순으로 봅니다. 상세(`GET /admin/articles/{id}`)에는 최근 5건만 들어 있어서, 그보다 더 거슬러 올라가야 할 때 이 엔드포인트를 부릅니다. "이 공지가 왜 다시 검수 대기로 내려갔는가" 를 추적하는 화면입니다.**

- **Method / Endpoint: `GET /api/v1/admin/articles/{articleId}/status-logs`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |

## Path Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| articleId | Long | 공지 ID | **필수** |

> **페이징이 없습니다.** `page`·`size`·`sort` 를 보내도 무시되고 전체 이력이 한 번에 내려옵니다.
> 한 공지의 상태 이력은 많아야 수십 줄이라 자를 이유가 없습니다.

## Request Sample

```
GET /api/v1/admin/articles/42/status-logs
```

# Response

### 이력은 누가 쓰는가

상태 변경 기록은 **DB 트리거가** 남깁니다. 애플리케이션은 "누가" 와 "왜" 를 트랜잭션에 알려주기만 합니다.

- **누가** — 로그인한 관리자 ID 가 트랜잭션 시작 시 자동으로 주입됩니다
- **왜** — 벌크 요청의 `memo` 값이 상태를 바꾸기 직전에 들어갑니다

그래서 `changed_by` 가 비어 있으면 **애플리케이션을 거치지 않은 변경**입니다.
크롤러가 원본 수정을 감지해 강등시켰거나, 스케줄러가 예약 발행한 경우입니다.
화면에는 "시스템" 으로 표시하세요.

## Response Param

`data` 가 **배열 자체**입니다. `data.content` 로 감싸져 있지 않습니다.

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Array | 상태 변경 이력 (최신순). 이력이 없으면 빈 배열 |
| data[].id | Long | 이력 ID |
| data[].from_status | String | 이전 상태. **최초 생성이면 필드가 빠집니다** |
| data[].to_status | String | 바뀐 상태 |
| data[].changed_by | Long | 변경한 관리자 ID. **없으면 시스템(크롤러·스케줄러)** |
| data[].changed_by_name | String | 변경한 관리자 이름. 시스템 변경이면 필드가 빠집니다 |
| data[].memo | String | 변경 사유. 벌크 요청의 `memo` 값. 안 보냈으면 필드가 빠집니다 |
| data[].created_at | String | 변경 시각 (ISO-8601 offset) |
| error | Object | 에러 정보 (성공 시 null) |

정렬은 `created_at` 내림차순, 같은 시각이면 `id` 내림차순입니다.
**같은 시각이 흔합니다** — 일괄 처리는 한 트랜잭션이라 `now()` 가 고정이고,
30건을 한 번에 배포하면 30줄의 `created_at` 이 완전히 같습니다.

> **`changed_by` 는 객체가 아니라 숫자입니다.** 이름은 `changed_by_name` 이라는
> 별도 필드로 나란히 내려갑니다. 두 필드는 항상 함께 있거나 함께 없습니다 —
> 시스템 변경이면 둘 다 빠집니다.

> **`memo` 는 없을 수 있습니다.** 사유를 빠뜨린 요청은 오류가 아니라 메모 없는 이력으로 남습니다.
> 화면에서 `memo` 가 항상 있다고 가정하면 안 됩니다.

### 이력에 나타나는 특이한 줄들

| 모양 | 무슨 일이 있었나 |
| --- | --- |
| `from_status` 없음 | 공지가 처음 만들어진 줄 |
| `from_status` == `to_status` | **병합** 으로 다른 공지를 흡수한 줄. 상태가 안 바뀐 사건이라 두 값이 같습니다. `memo` 에 흡수한 공지 번호가 접두어로 붙습니다 |
| `PENDING_REVIEW → READY_TO_PUBLISH` 와 `READY_TO_PUBLISH → PUBLISHED` 가 같은 시각에 연달아 | **재검수 완료**. 한 번의 요청이지만 전이 규칙을 그대로 밟으므로 이력에는 두 줄이 남습니다 |

> **병합된 공지의 이력이 섞여 들어옵니다.** 병합은 흡수된 공지의 상태 이력을
> 대상 공지로 **옮깁니다.** 그래서 병합 이후 이 목록에는 원래 다른 공지에서 일어난 변경이
> 함께 보입니다. 시간 순서가 뒤엉킨 것처럼 보이면 대개 그 이유입니다 —
> `from_status == to_status` 인 병합 줄을 기준으로 읽으세요.

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | articleId: 값의 형식이 올바르지 않습니다. | 경로 변수가 숫자가 아님 |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | `ROLE_ADMIN` 이 아님 |
| 404 | ARTICLE_NOT_FOUND | 존재하지 않는 공지입니다. | 해당 ID 의 공지 없음 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> **이력이 0건인 것과 공지가 없는 것은 다릅니다.** 공지 존재 여부를 먼저 확인하므로,
> 공지가 없으면 빈 배열이 아니라 404 입니다. 공지는 있는데 이력이 없으면 `data: []` 입니다.

> **영구 삭제된 공지의 이력은 조회할 수 없습니다.** 공지를 지우면 상태 이력도 CASCADE 로
> 함께 사라져 404 가 됩니다. 현재 관리자 조작 전용 감사 테이블이 없어서
> 영구 삭제 기록은 애플리케이션 로그에만 남습니다.
