# 공지 상태 일괄 변경

**선택한 공지들의 검수 상태를 한 번에 바꿉니다. 검수 목록에서 여러 건을 골라 "검수 완료" · "반려" 같은 버튼을 눌렀을 때 부릅니다. 부분 성공을 허용하며 실패 건은 사유와 함께 돌려줍니다.**

- **Method / Endpoint: `POST /api/v1/admin/articles/bulk/status`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |
| Content-Type | application/json | | **필수** |

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| ids | Array&lt;Long&gt; | 대상 게시글 번호. **1건 이상 200건 이하**. 원소에 `null` 불가 | **필수** |
| status | String | 바꿀 상태 | **필수** |
| memo | String | 상태 이력에 남길 사유. 최대 500자 | 선택 |

> 요청 키는 `ids` 입니다 — `article_ids` 가 아닙니다. 경로가 이미 `/admin/articles/bulk/*` 라
> 무엇의 번호인지는 경로가 말해 줍니다.
>
> **200건 상한은 잠금 때문입니다.** 한 요청이 공지 수천 건을 건드리면 그동안 그 행들에 대한
> 크롤러 갱신이 전부 대기합니다.

### `status` 허용 값과 전이 규칙

`PENDING_REVIEW` · `READY_TO_PUBLISH` · `DRAFT` · `PUBLISHED` · `TRASHED`

**두 가지 검사를 모두 통과해야 합니다.**

1. **상태 집합** — 출처 유형에 그 상태가 있는지. DB CHECK(`ck_articles_status_by_source`) 와 앱이 같이 봅니다

| 상태 | 쓸 수 있는 출처 |
| --- | --- |
| `PENDING_REVIEW` | `SCHOOL` 전용 |
| `READY_TO_PUBLISH` | `SCHOOL` 전용 |
| `DRAFT` | `CLUB` 전용 |
| `PUBLISHED` | 공용 |
| `TRASHED` | 공용 |

2. **상태 전이** — 지금 상태에서 그리로 갈 수 있는지. **이건 앱만 압니다.** DB 는 전이 표를 모릅니다

| 현재 상태 | 갈 수 있는 상태 |
| --- | --- |
| `PENDING_REVIEW` | `READY_TO_PUBLISH`, `TRASHED` |
| `READY_TO_PUBLISH` | `PUBLISHED`, `PENDING_REVIEW`(반려), `TRASHED` |
| `DRAFT` | `PUBLISHED`, `TRASHED` |
| `PUBLISHED` | `READY_TO_PUBLISH`(배포 취소), `PENDING_REVIEW`, `TRASHED` |
| `TRASHED` | **없음** — 복구는 `POST /admin/articles/bulk/restore` 로만 |

원칙은 "역방향은 전부 허용, 단계 건너뛰기만 금지" 입니다. 반려·배포 취소는 운영에서 흔한 동작이라
막으면 관리자가 우회 경로를 찾게 됩니다. 반대로 `PENDING_REVIEW → PUBLISHED` 를 허용하면
검수 단계가 있으나 마나가 됩니다.

> **발행된 동아리 공지가 갈 수 있는 곳은 `TRASHED` 뿐입니다.** 전이 표상 `PUBLISHED` 에서
> `READY_TO_PUBLISH` · `PENDING_REVIEW` 로 내려갈 수 있지만 그 둘은 `SCHOOL` 전용이라
> 상태 집합 검사에서 걸립니다. 발행한 동아리 공지를 내리려면 휴지통에 넣었다 복구하는 경로를 씁니다.

> **같은 상태로는 바꿀 수 없습니다.** `PUBLISHED` 인 공지를 다시 `PUBLISHED` 로 보내면
> `INVALID_STATE_TRANSITION` 으로 **실패 처리**됩니다. 무의미한 전이가 감사 로그를 더럽히지
> 않게 하려는 것입니다. 화면에서 이미 그 상태인 항목을 선택 해제해 주는 편이 좋습니다.

### `memo` 는 DB 트리거가 읽습니다

상태 이력(`article_status_logs`)을 기록하는 주체는 앱이 아니라 **DB 트리거**입니다.
트리거는 "왜" 를 알 수 없어서 앱이 트랜잭션 변수(`app.status_change_memo`)로 넘겨줍니다.

- 안 보내면 오류가 아니라 `memo = NULL` 로 남습니다
- 500자를 넘으면 **잘려서** 저장됩니다(거부가 아닙니다). Bean Validation 이 먼저 400 으로 막지만, 그 검사를 통과한 값도 저장 직전에 한 번 더 잘립니다
- 실패한 건은 트랜잭션이 롤백되므로 그 건의 이력도 사유도 남지 않습니다

## Request Sample

```json
POST /api/v1/admin/articles/bulk/status
{
  "ids": [11, 12, 13],
  "status": "READY_TO_PUBLISH",
  "memo": "1차 검수 완료"
}
```

```json
// 반려 — READY_TO_PUBLISH 에서 검수 대기로 되돌립니다
POST /api/v1/admin/articles/bulk/status
{
  "ids": [21],
  "status": "PENDING_REVIEW",
  "memo": "기간 정보 누락. 원본 확인 필요"
}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.succeeded | Array&lt;Long&gt; | 처리에 성공한 게시글 번호 |
| data.failed | Array | 실패한 건 |
| data.failed[].id | Long | 실패한 게시글 번호 |
| data.failed[].code | String | 실패 사유 코드 (공통 Error 표와 같은 체계) |
| data.failed[].message | String | 사람이 읽을 사유 |

> **`failed` 가 비어 있지 않아도 HTTP 는 200 입니다.** 부분 성공이 정상 경로이기 때문입니다 —
> 프론트는 상태 코드가 아니라 `failed` 배열을 보고 판단해야 합니다.
>
> 요청한 번호는 **전부** 둘 중 한쪽에 나타납니다. 이미 지워졌거나 없는 번호도 조용히 빠지지 않고
> `failed` 에 담깁니다. 30건을 골랐는데 28건만 처리된 것을 모르는 상황을 만들지 않기 위해서입니다.
> 중복으로 담긴 번호는 한 번으로 합쳐지므로 `succeeded` + `failed` 의 개수가 요청 개수보다
> 적을 수 있습니다.

> **건별로 트랜잭션이 나뉩니다.** 한 건이 실패해도 이미 성공한 건은 그대로 커밋됩니다.
> 되돌리려면 반대 방향 전이를 다시 요청해야 합니다.

### `data.failed[].code` 로 올 수 있는 값

| code | 원인 |
| --- | --- |
| ARTICLE_NOT_FOUND | 그 번호의 공지가 없음 |
| INVALID_STATE_TRANSITION | 전이 표에 없는 이동. 같은 상태로의 변경 포함 |
| INVALID_STATUS_FOR_SOURCE | 출처 유형에 없는 상태 (`CLUB` + `READY_TO_PUBLISH` 등) |
| CONCURRENT_MODIFICATION | 그 건을 다른 관리자가 먼저 수정 |
| RESOURCE_BUSY | 교착·직렬화 실패. **재시도하면 성공할 수 있습니다** |
| INVALID_INPUT_VALUE | DB CHECK 위반 (23514) |
| INTERNAL_SERVER_ERROR | 매핑되지 않은 실패. 서버 로그에 원문이 남습니다 |

## Response Sample

```json
{
  "success": true,
  "data": {
    "succeeded": [11, 12],
    "failed": [
      {
        "id": 13,
        "code": "INVALID_STATE_TRANSITION",
        "message": "허용되지 않은 상태 변경입니다."
      }
    ]
  }
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | ids: 대상 공지를 선택해 주세요. | `ids` 가 비었거나 없음 |
| 400 | INVALID_INPUT_VALUE | ids: 한 번에 200건까지 처리할 수 있습니다. | `ids` 가 200건 초과 |
| 400 | INVALID_INPUT_VALUE | status: 변경할 상태를 지정해 주세요. | `status` 누락 |
| 400 | INVALID_INPUT_VALUE | memo: 사유는 500자를 넘을 수 없습니다. | `memo` 500자 초과 |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | JSON 파싱 실패, `status` 가 enum 에 없는 문자열 |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | 관리자가 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 위 표는 **요청 전체가 거부되는 경우**만입니다. 개별 건의 실패는 HTTP 에러가 아니라
> `data.failed[]` 로 내려갑니다.
