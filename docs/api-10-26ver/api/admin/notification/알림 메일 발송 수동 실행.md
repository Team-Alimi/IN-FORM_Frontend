# 알림 메일 발송 수동 실행

**알림 메일 발송 배치를 지금 한 번 돌립니다. 5분 주기를 기다리지 않고 메일을 확인할 때 씁니다.**

- **Method / Endpoint: `POST /api/v1/admin/notifications/email-run`**
- **Auth Required: Required (Admin)**

> **주기 배치와 완전히 같은 코드입니다.** 테스트용 별도 경로가 아니라 같은 메서드를 부릅니다 —
> 경로가 갈라지면 테스트에서 본 결과가 운영을 대변하지 못합니다.

> ## ⚠ 실제로 메일이 나갑니다
>
> **되돌릴 수 없습니다.** 누르기 전에 대상이 누구인지 확인하세요.
> 대상은 아래 네 조건을 **모두** 만족하는 알림입니다.
>
> | 조건 | |
> |---|---|
> | `notifications.email_sent_at IS NULL` | 아직 메일을 안 보냄 |
> | `created_at` 이 `max-age`(기본 24시간) 안 | 오래된 알림을 소급 발송하지 않음 |
> | `users.email_notification_enabled = TRUE` | 수신을 켜 둔 사용자 |
> | `users.status = 'ACTIVE'` | 탈퇴자 제외 |

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |

본문도 파라미터도 없습니다. **대상을 지정할 수 없습니다** — 특정 사용자에게만 보내는 경로를
열면 그게 곧 "관리자가 임의로 메일을 쏘는 버튼" 이 됩니다.

## Request Sample

```
POST /api/v1/admin/notifications/email-run
```

# 테스트 흐름

```
1) 수신 주소를 SES 에서 검증합니다  ← 프로덕션 액세스 승인 전에는 필수
2) 공지의 마감일(ends_on)을 내일로 두고 테스트 계정으로 북마크합니다
3) POST /api/v1/admin/notifications/deadline-run   →  알림 생성
4) POST /api/v1/admin/notifications/email-run      →  메일 발송
5) 메일함 확인
```

> **2번까지는 `마감 알림 수동 실행.md` 와 같습니다.** 알림이 없으면 보낼 것도 없습니다.

> **1번을 건너뛰면 발송이 거부됩니다.** SES 샌드박스에서는 발신 도메인과
> **수신 주소 양쪽**이 검증된 identity 여야 합니다.
> 그 경우 응답은 `failed > 0` 이고, 알림은 `email_sent_at` 이 NULL 로 남아 재시도됩니다.

# 여러 번 눌러도 같은 메일이 두 번 가지 않습니다

보낸 알림은 `email_sent_at` 이 찍혀 대상에서 빠집니다. 두 번째 호출은 보통 `sent: 0` 입니다.

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data.sent | Integer | 보내고 기록까지 끝낸 건수 |
| data.failed | Integer | 발송이 실패해 **다음 주기에 재시도될** 건수 |
| data.duplicated | Integer | 보냈는데 기록이 이미 있던 건수. **0 이 아니면 중복 발송** |
| data.targeted | Integer | 이번 실행이 집어 온 건수 |

## Response Sample

```json
{
  "success": true,
  "data": {
    "sent": 3,
    "failed": 0,
    "duplicated": 0,
    "targeted": 3
  }
}
```

## 응답을 읽는 법

| 값 | 뜻 | 할 일 |
|---|---|---|
| `targeted: 0` | 보낼 것이 없었음 / `MAIL_FROM` 미설정으로 발송 비활성 / 다른 실행이 락 보유 | **셋이 구분되지 않습니다 — 로그를 보세요** |
| `failed > 0` | 그만큼 재시도 대상으로 남음 | 로그의 알림 id 로 원인 확인 |
| `duplicated > 0` | **같은 메일이 중복 발송됐을 수 있음** | 배치 락(Redis) 상태 확인 |
| `sent + failed + duplicated < targeted` | 연속 실패로 중단됨 | 자격증명·리전·발신 한도 확인 |

> **`targeted: 0` 이 가장 자주 보게 될 값입니다.** `MAIL_FROM` 이 서버 `.env` 에 없으면
> 발송이 조용히 비활성이고, 그 사실은 로그에 **한 번만** 경고로 남습니다
> (`MAIL_FROM 이 없어 알림 메일을 보내지 않습니다`).

# ★ 연속 5건 실패하면 중단합니다

주소 하나가 잘못됐다고 나머지 전원의 메일을 막을 이유는 없어서 건당 실패는 넘어갑니다.
반대로 **연달아** 실패하는 것은 주소 문제가 아니라 자격증명·리전·발신 한도처럼
전체에 걸린 문제입니다. 그 상태로 끝까지 돌리면 한도를 때리는 호출만 반복합니다.

중단된 나머지는 `email_sent_at` 이 NULL 로 남아 다음 주기에 이어집니다.

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | `ROLE_ADMIN` 이 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 조회·락 획득 단계의 실패 |

> **개별 발송 실패는 500 이 아닙니다.** `failed` 로 집계해 200 으로 돌려줍니다 —
> 한 통이 실패해도 나머지는 보내야 하고, 어느 쪽이 몇 건인지는 응답에 있습니다.
>
> 주기 배치는 예외를 삼키고 로그만 남기지만(스케줄러 스레드가 죽으면 다음 주기도
> 돌지 않기 때문입니다) 이쪽은 500 으로 내보냅니다.

# 왜 5분 주기인가

알림 생성은 하루 한 번(09:00)이지만 발송은 5분마다 돕니다.
SES 가 일시적으로 실패하면 `email_sent_at` 이 NULL 로 남아 재시도되는데,
하루 한 번이면 그 재시도가 **24시간 뒤**입니다 —
마감 하루 전 알림이 마감 당일에 도착하면 보낸 의미가 없습니다.
