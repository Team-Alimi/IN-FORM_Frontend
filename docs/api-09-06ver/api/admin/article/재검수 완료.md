# 재검수 완료

**크롤러가 원본 수정을 감지해 검수 대기로 내려간 공지를 다시 배포합니다. 그 공지는 지금 이 순간 피드에서 사라져 있으므로, 검수 통과와 발행을 한 번에 처리해 공백을 줄입니다. 재검수 대기 목록(`GET /admin/articles?needs_review=true`)의 "재검수 완료" 버튼이 부릅니다.**

- **Method / Endpoint: `POST /api/v1/admin/articles/bulk/review-complete`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |
| Content-Type | application/json | | **필수** |

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| ids | Array&lt;Long&gt; | 대상 게시글 번호. **1건 이상 200건 이하**. 원소에 `null` 불가 | **필수** |
| memo | String | 상태 이력에 남길 사유. 최대 500자 | 선택 |

> **`memo` 를 받습니다.** 구판 명세 표에는 body 가 `ids` 뿐이라고 적혀 있지만
> 실제로는 사유를 함께 받습니다. 사유는 **두 줄의 이력 모두**에 같은 값으로 남습니다.

### "재검수 대기" 의 정의

`status = PENDING_REVIEW` **이면서** `published_at` 이 채워져 있는 공지입니다.

`published_at` 이 "한 번이라도 배포된 적 있음" 의 표식입니다. DB CHECK 가 `PUBLISHED` 일 때
이 값을 강제하고 트리거가 최초 발행 때만 찍으므로, 배포를 거친 공지는 이후 어떤 상태로 가도
이 표식을 잃지 않습니다.

> **한 번도 배포된 적 없는 공지는 실패로 기록됩니다.** 그건 재검수가 아니라 **최초 검수**이고,
> 발행 여부를 사람이 따로 판단해야 합니다. 여기서 통과시키면 "재검수 완료" 버튼 하나로
> 신규 수집분이 검수 없이 바로 배포됩니다. 신규 건은
> `POST /admin/articles/bulk/status` → `POST /admin/articles/bulk/publish` 순서로 처리하세요.

> `PENDING_REVIEW` 는 `SCHOOL` 전용 상태입니다. 따라서 이 API 의 대상은 사실상 학교 공지뿐입니다.

### 전이는 두 단계입니다

`PENDING_REVIEW` → `READY_TO_PUBLISH` → `PUBLISHED` 를 **순서대로** 밟습니다.

- 전이 규칙을 우회하지 않습니다. 두 단계 모두 규칙 검사를 거칩니다
- **감사 이력에도 두 줄이 남습니다.** 실제로 일어난 일이 두 단계이므로 그게 사실입니다
- 한 번에 `PENDING_REVIEW → PUBLISHED` 로 점프하면 전이 표에 없는 이동이 감사 로그에 남아, 나중에 규칙 위반처럼 보이는 기록이 됩니다

### 내용 수정이 필요하면 먼저 고치세요

이 API 는 **상태만** 바꿉니다. 원본이 바뀐 내용을 반영하려면
`PATCH /admin/articles/{articleId}` 로 먼저 고친 뒤 부르세요.

## Request Sample

```json
POST /api/v1/admin/articles/bulk/review-complete
{
  "ids": [88, 91],
  "memo": "원본 기간 변경 확인함"
}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.succeeded | Array&lt;Long&gt; | 재검수 완료 + 배포까지 끝난 게시글 번호 |
| data.failed | Array | 실패한 건 |
| data.failed[].id | Long | 실패한 게시글 번호 |
| data.failed[].code | String | 실패 사유 코드 |
| data.failed[].message | String | 사람이 읽을 사유 |

> **`failed` 가 비어 있지 않아도 HTTP 는 200 입니다.** 프론트는 상태 코드가 아니라
> `failed` 배열을 보고 판단해야 합니다.
>
> 요청한 번호는 **전부** 둘 중 한쪽에 나타납니다. 중복으로 담긴 번호는 한 번으로 합쳐집니다.
> 건별로 트랜잭션이 나뉘므로 한 건이 실패해도 이미 배포된 건은 그대로 남습니다.
>
> 두 단계 전이가 **한 건 = 한 트랜잭션** 안에서 일어납니다. 중간(`READY_TO_PUBLISH`)에서
> 멈춘 채 끝나는 경우는 없습니다.

### `data.failed[].code` 로 올 수 있는 값

| code | 원인 |
| --- | --- |
| ARTICLE_NOT_FOUND | 그 번호의 공지가 없음 |
| INVALID_STATE_TRANSITION | 재검수 대기가 아님 — `PENDING_REVIEW` 가 아니거나 한 번도 배포된 적 없음 |
| INVALID_STATUS_FOR_SOURCE | 출처 유형에 없는 상태로의 전이 |
| CONCURRENT_MODIFICATION | 그 건을 다른 관리자가 먼저 수정 |
| RESOURCE_BUSY | 교착·직렬화 실패. 재시도하면 성공할 수 있습니다 |
| INTERNAL_SERVER_ERROR | 매핑되지 않은 실패 |

## Response Sample

```json
{
  "success": true,
  "data": {
    "succeeded": [88],
    "failed": [
      {
        "id": 91,
        "code": "INVALID_STATE_TRANSITION",
        "message": "재검수 대기 중인 공지가 아닙니다. 신규 수집분은 일반 검수 흐름으로 처리해 주세요. articleId=91"
      }
    ]
  }
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | ids: 대상 공지를 선택해 주세요. | `ids` 가 비었거나 없음 |
| 400 | INVALID_INPUT_VALUE | ids: 한 번에 200건까지 처리할 수 있습니다. | `ids` 가 200건 초과 |
| 400 | INVALID_INPUT_VALUE | memo: 사유는 500자를 넘을 수 없습니다. | `memo` 500자 초과 |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | JSON 파싱 실패 |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | 관리자가 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 위 표는 **요청 전체가 거부되는 경우**만입니다. 개별 건의 실패는 `data.failed[]` 로 내려갑니다.
