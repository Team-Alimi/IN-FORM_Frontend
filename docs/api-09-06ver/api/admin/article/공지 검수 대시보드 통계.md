# 공지 검수 대시보드 통계

**관리자 검수 대시보드 상단의 카드 숫자를 한 번에 내려줍니다. 상태별 건수 여섯 개와 "중복 의심"·"재검수 대기" 두 축으로 구성됩니다. 관리자가 검수 화면에 들어올 때 한 번 호출하고, 벌크 처리를 끝낸 뒤 카드를 갱신할 때 다시 부릅니다.**

- **Method / Endpoint: `GET /api/v1/admin/articles/stats`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |

## Request Sample

```
GET /api/v1/admin/articles/stats
```

# Response

### 숫자 일곱 개가 어떻게 세어지는지

| 필드 | 세는 조건 |
| --- | --- |
| `draft` | `status = 'DRAFT'` |
| `pending_review` | `status = 'PENDING_REVIEW'` |
| `ready_to_publish` | `status = 'READY_TO_PUBLISH'` |
| `published` | `status = 'PUBLISHED'` |
| `trashed` | `status = 'TRASHED'` |
| `duplicate_suspected` | `status <> 'TRASHED'` **그리고** `similarity_score >= 임계값` |
| `needs_review` | `status = 'PENDING_REVIEW'` **그리고** `published_at IS NOT NULL` |

일곱 개를 한 문장(`count(*) FILTER (...)`)으로 셉니다. 세 번 나눠 세면 그 사이에
크롤러가 새 공지를 넣어 카드끼리 앞뒤가 안 맞을 수 있어서, 같은 스냅샷에서 나온 숫자로 맞췄습니다.

> **합계를 "전체 공지 수" 로 그리면 안 됩니다.**
> 앞의 다섯(`draft`·`pending_review`·`ready_to_publish`·`published`·`trashed`)은 서로 배타적이라
> 더하면 전체가 됩니다. 하지만 뒤의 둘은 그 다섯과 **겹칩니다.**
> - `needs_review` 는 `pending_review` 의 **부분집합**입니다. 두 번 세지 마세요
> - `duplicate_suspected` 는 상태와 독립된 축이라 어느 상태에나 걸릴 수 있습니다

### `needs_review` 의 판정식이 명세와 다른 이유

구판 명세는 `review_requested_at IS NOT NULL` 이라고 적고 있지만 **그 컬럼은 스키마에서 제거됐습니다.**
재검수 정책이 "노출 유지 + 플래그" 에서 **"검수 대기로 강등"** 으로 바뀌었기 때문입니다.
크롤러가 원본 수정을 감지하면 `status` 를 `PENDING_REVIEW` 로 내리는데,
한 번이라도 배포됐던 공지는 `published_at` 이 남아 있습니다.
그래서 "재검수 대기" 와 "한 번도 배포된 적 없는 신규 수집분" 이 `published_at` 하나로 갈립니다.

### `duplicate_suspected` 의 임계값

`inform.review.similarity-threshold` 설정값이고 **현재 80** 입니다(0~100 척도).
운영하며 조정하는 값이라 DB 가 아니라 애플리케이션 설정에 있습니다 — 배포만으로 바뀝니다.
`similarity_score` 도 같은 0~100 척도입니다(`numeric(5,2)`). 0~1 이 아닙니다.

`status <> 'TRASHED'` 를 함께 거는 이유는 목록(`GET /admin/articles`)의 기본 조건이 그렇기 때문입니다.
카드가 휴지통까지 세면 관리자가 눌러서 이동한 목록에는 그만큼이 없어 **카드 숫자와 목록이 어긋납니다.**

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.draft | Long | 임시저장 (`DRAFT`). 동아리 공지 전용 상태입니다 |
| data.pending_review | Long | 검수 대기 (`PENDING_REVIEW`). 학교 공지 전용 상태입니다 |
| data.duplicate_suspected | Long | 중복 의심. 휴지통 제외 |
| data.ready_to_publish | Long | 발행 대기 (`READY_TO_PUBLISH`) |
| data.published | Long | 배포됨 (`PUBLISHED`) |
| data.trashed | Long | 휴지통 (`TRASHED`) |
| data.needs_review | Long | 재검수 대기. `pending_review` 의 부분집합 |
| error | Object | 에러 정보 (성공 시 null) |

> 일곱 개 모두 원시 타입이라 **0 이어도 필드가 사라지지 않습니다.** 항상 전부 내려옵니다.

## Response Sample

```json
{
  "success": true,
  "data": {
```

### 카드에서 목록으로 넘어갈 때 쓸 파라미터

| 카드 | 이동할 목록 |
| --- | --- |
| `draft` | `GET /admin/articles?status=DRAFT` |
| `pending_review` | `GET /admin/articles?status=PENDING_REVIEW` |
| `ready_to_publish` | `GET /admin/articles?status=READY_TO_PUBLISH` |
| `published` | `GET /admin/articles?status=PUBLISHED` |
| `trashed` | `GET /admin/articles/trash` |
| `needs_review` | `GET /admin/articles?needs_review=true` |
| `duplicate_suspected` | **정확히 대응하는 파라미터가 없습니다** |

> **`duplicate_suspected` 카드는 목록과 숫자가 맞지 않습니다.**
> 가장 가까운 것이 `GET /admin/articles?needs_check=true` 인데, 그쪽은 유사도뿐 아니라
> 기간 누락·본문 부실·분류 미지정까지 함께 잡는 **더 넓은 조건**이라 목록 건수가 카드보다 큽니다.
> 화면에서 두 숫자를 같은 것으로 다루지 마세요.

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | `ROLE_ADMIN` 이 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 이 엔드포인트는 파라미터가 없어서 애플리케이션이 던지는 `BusinessException` 이 하나도 없습니다.
> 인증·권한과 서버 오류를 빼면 실패 경로가 없습니다.
