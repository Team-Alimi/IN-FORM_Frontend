# 공지 복구

**휴지통에 있는 공지를 되살립니다. 휴지통 목록 화면의 "복원" 버튼이 부릅니다. 목적지를 고를 수 없고, 상태 이력이 기억하는 휴지통 직전 상태로만 돌아갑니다.**

- **Method / Endpoint: `POST /api/v1/admin/articles/bulk/restore`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |
| Content-Type | application/json | | **필수** |

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| ids | Array&lt;Long&gt; | 대상 게시글 번호. **1건 이상 200건 이하**. 원소에 `null` 불가 | **필수** |
| memo | String | 상태 이력에 남길 사유. 최대 500자 | 선택 |

> **`memo` 를 받습니다.** 구판 명세 표에는 `bulk/restore` 의 body 가 `ids` 뿐이라고 적혀 있지만
> 실제로는 사유를 함께 받아 상태 이력에 남깁니다.

### 목적지를 지정할 수 없습니다

요청에 "어디로 되돌릴지" 를 넣는 자리가 없습니다. 서버가 `article_status_logs` 에서
**가장 최근의 `to_status = TRASHED` 기록**을 찾아 그 줄의 `from_status` 로 되돌립니다.

관리자가 목적지를 고를 수 있게 하면 휴지통이 상태 전이 규칙의 우회로가 됩니다 —
검수 대기 공지를 휴지통에 넣었다가 곧바로 발행 상태로 꺼낼 수 있게 됩니다.

- 휴지통에 넣었다 꺼냈다를 반복한 공지는 이력이 여러 줄이라 **가장 최근 기록**만 봅니다
- 복구할 곳을 미리 보여 주려면 `GET /admin/articles/trash` 의 `previous_status` 를 쓰세요. 같은 값입니다
- 앱을 거치지 않고 `TRASHED` 가 된 공지(DB 직접 수정, 데이터 이관 등)는 **복구할 수 없습니다.** 이력이 없으면 어디로 되돌릴지 알 방법이 없습니다

> **직전 상태가 지금 출처 유형에 맞지 않으면 실패합니다.** 실무에서 보기 드물지만,
> 이력에 남은 상태가 그 공지의 출처에서 쓸 수 없는 값이면 `INVALID_STATUS_FOR_SOURCE` 입니다.

## Request Sample

```json
POST /api/v1/admin/articles/bulk/restore
{
  "ids": [41, 42],
  "memo": "오분류. 되살림"
}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.succeeded | Array&lt;Long&gt; | 복구에 성공한 게시글 번호 |
| data.failed | Array | 실패한 건 |
| data.failed[].id | Long | 실패한 게시글 번호 |
| data.failed[].code | String | 실패 사유 코드 |
| data.failed[].message | String | 사람이 읽을 사유 |

> **응답에 "어느 상태로 돌아갔는지" 는 없습니다.** `succeeded` 는 번호 목록일 뿐입니다.
> 복구 후 상태를 화면에 반영하려면 목록을 다시 조회하거나, 요청 전에 받아 둔
> `previous_status` 를 쓰세요.
>
> **`failed` 가 비어 있지 않아도 HTTP 는 200 입니다.** 요청한 번호는 **전부** 둘 중 한쪽에
> 나타나고, 중복으로 담긴 번호는 한 번으로 합쳐집니다. 건별로 트랜잭션이 나뉘므로
> 한 건이 실패해도 이미 복구된 건은 그대로 남습니다.

### `data.failed[].code` 로 올 수 있는 값

| code | 원인 |
| --- | --- |
| ARTICLE_NOT_FOUND | 그 번호의 공지가 없음 |
| NOT_IN_TRASH | 휴지통 이동 이력이 없거나(`복구할 직전 상태를 찾을 수 없습니다`), 지금 상태가 `TRASHED` 가 아님 |
| INVALID_STATUS_FOR_SOURCE | 이력에 남은 직전 상태를 그 공지의 출처에서 쓸 수 없음 |
| CONCURRENT_MODIFICATION | 그 건을 다른 관리자가 먼저 수정 |
| RESOURCE_BUSY | 교착·직렬화 실패. 재시도하면 성공할 수 있습니다 |
| INTERNAL_SERVER_ERROR | 매핑되지 않은 실패 |

> **휴지통이 아닌 공지를 섞어 보내면 `NOT_IN_TRASH` 로 실패합니다.** 다만 그 공지가
> 과거에 한 번 휴지통에 갔다 온 적이 있으면 이력 조회는 통과하고 그다음 검사에서 걸립니다 —
> 두 경우 모두 같은 코드지만 메시지가 다릅니다.

## Response Sample

```json
{
  "success": true,
  "data": {
    "succeeded": [41],
    "failed": [
      {
        "id": 42,
        "code": "NOT_IN_TRASH",
        "message": "복구할 직전 상태를 찾을 수 없습니다. articleId=42"
      }
    ]
  }
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | ids: 대상 공지를 선택해 주세요. | `ids` 가 비었거나 없음 |
| 400 | INVALID_INPUT_VALUE | ids: 한 번에 200건까지 처리할 수 있습니다. | `ids` 가 200건 초과 |
| 400 | INVALID_INPUT_VALUE | memo: 사유는 500자를 넘을 수 없습니다. | `memo` 500자 초과 |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | JSON 파싱 실패 |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | 관리자가 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 위 표는 **요청 전체가 거부되는 경우**만입니다. 개별 건의 실패(`NOT_IN_TRASH` 포함)는
> HTTP 에러가 아니라 `data.failed[]` 로 내려갑니다.
