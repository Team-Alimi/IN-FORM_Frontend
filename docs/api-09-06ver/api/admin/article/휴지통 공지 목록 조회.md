# 휴지통 공지 목록 조회

**휴지통으로 보낸 공지를 버린 순서대로 봅니다. 각 항목에 "휴지통에 들어가기 직전 상태"(`previous_status`)가 함께 내려가서, 복원 버튼이 어디로 되돌릴지 미리 보여줄 수 있습니다. 복구(`POST /admin/articles/bulk/restore`)와 영구 삭제(`POST /admin/articles/bulk/delete`)는 이 화면에서 시작합니다.**

- **Method / Endpoint: `GET /api/v1/admin/articles/trash`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |

## Query Param

| Name | Type | Description | Required | Default |
| --- | --- | --- | --- | --- |
| page | Integer | 조회할 페이지 번호 (**1부터 시작**) | 선택 | 1 |
| size | Integer | 페이지당 건수. **상한 50** | 선택 | 20 |

> **필터도 정렬도 없습니다.** `status`·`keyword`·`vendor_id` 같은 목록 파라미터는 여기서 동작하지 않고,
> `sort` 를 보내도 **조용히 무시**됩니다. 정렬은 `updated_at desc, id desc` 로 고정입니다 —
> 휴지통은 "방금 버린 것" 부터 보는 화면이라 다른 축이 필요하지 않습니다.
> 잘못된 `sort` 값을 보내도 `INVALID_SORT_PROPERTY` 가 나지 않습니다.
> 목록(`GET /admin/articles`)과 달리 정렬 검증기를 거치지 않기 때문입니다.

## Request Sample

```
GET /api/v1/admin/articles/trash

GET /api/v1/admin/articles/trash?page=2&size=50
```

# Response

### `GET /admin/articles?status=TRASHED` 와의 차이

거의 같은 목록이 나오지만 **`previous_status` 가 따라붙는 것은 이 엔드포인트뿐입니다.**
`articles.status` 는 `TRASHED` 로 덮여 있어 원래 상태를 알 수 없고,
그 값은 상태 이력(`article_status_logs`)에서 따로 읽어와야 합니다.
`GET /admin/articles?status=TRASHED` 는 그 조회를 하지 않으므로 `previous_status` 가 비어 옵니다.

`previous_status` 는 `to_status = 'TRASHED'` 인 이력 중 **가장 최근 한 줄**의 `from_status` 입니다.
휴지통에 넣었다 꺼냈다를 반복한 공지는 이력이 여러 줄이라, 가장 오래된 것을 집으면
엉뚱한 상태로 복구됩니다.

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.page_info | Object | 페이징 정보 |
| data.page_info.current_page | Integer | 현재 페이지 번호 (1부터). 0건이어도 1 |
| data.page_info.size | Integer | 페이지당 건수 |
| data.page_info.total_pages | Integer | 전체 페이지 수. 0건이면 0 |
| data.page_info.total_items | Long | 전체 건수 |
| data.page_info.has_next | Boolean | 다음 페이지 존재 여부 |
| data.content | Array | 휴지통 공지 목록 |
| data.content[].id | Long | 공지 ID |
| data.content[].source_type | String | `SCHOOL` \| `CLUB` |
| data.content[].status | String | **항상 `TRASHED`** |
| data.content[].title | String | 제목 |
| data.content[].starts_on | String | 시작일 (yyyy-MM-dd). 없으면 필드가 빠집니다 |
| data.content[].ends_on | String | 마감일 (yyyy-MM-dd). 없으면 필드가 빠집니다 |
| data.content[].deadline_status | String | 마감 상태 파생값 (`UPCOMING`/`OPEN`/`CLOSING_SOON`/`CLOSED`/`ALWAYS`) |
| data.content[].similarity_score | Number | 중복 의심 점수 0~100. 미판정이면 필드가 빠집니다 |
| data.content[].similar_article_id | Long | 중복 의심 상대 공지 ID. 미판정이면 필드가 빠집니다 |
| data.content[].updated_at | String | 내용 수정 시각 (ISO-8601 offset). **정렬 기준** |
| data.content[].last_status_change | String | 상태가 마지막으로 바뀐 시각 = 휴지통에 넣은 시각 |
| data.content[].created_by | Long | 작성 관리자 ID. 크롤러 수집분은 필드가 빠집니다 |
| data.content[].has_attachment | Boolean | 첨부 존재 여부. 영구 삭제 시 함께 지워질 파일이 있는지 |
| data.content[].previous_status | String | **휴지통 직전 상태.** 복원 버튼 문구의 근거 |
| data.content[].vendors | Array | 제공처 목록 |
| data.content[].vendors[].id | Long | 제공처 ID |
| data.content[].vendors[].name | String | 제공처 이름 |
| data.content[].vendors[].initial | String | 축약 표시 |
| data.content[].vendors[].type | String | `SCHOOL` \| `CLUB` |
| data.content[].categories | Array | 분류 목록 |
| data.content[].categories[].id | Long | 분류 ID |
| data.content[].categories[].name | String | 분류 이름 |
| error | Object | 에러 정보 (성공 시 null) |

> **`previous_status` 가 없는 항목이 있을 수 있습니다.** 앱을 거치지 않고 휴지통에 들어간 공지
> (직접 UPDATE, 마이그레이션 등)는 이력이 없어 필드 자체가 빠집니다.
> `null` 이 아니라 **키가 존재하지 않는다**는 점에 주의하세요.
>
> 이런 공지는 복구도 불가능합니다 — `POST /admin/articles/bulk/restore` 가
> 되돌릴 곳을 알 수 없어 `NOT_IN_TRASH` 로 실패합니다. `previous_status` 가 없는 행은
> 복원 버튼을 비활성화하는 편이 맞습니다.

> 복구는 **직전 상태로만** 갑니다. 관리자가 목적지를 고를 수 없습니다 —
> 고를 수 있게 하면 휴지통이 상태 전이 규칙의 우회로가 되어,
> 검수 대기 공지를 휴지통에 넣었다가 바로 배포 상태로 꺼낼 수 있게 됩니다.

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | `ROLE_ADMIN` 이 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 이 경로에서 애플리케이션이 던지는 `BusinessException` 은 없습니다.
> 조건 파라미터가 없어 검증에 걸릴 것이 없고, 결과가 0건이어도 200 입니다.

> **`size` 상한 초과는 오류가 아니라 절삭입니다.** `size=200` 은 400 이 아니라 50 으로 잘립니다.
> 실제 적용값은 `page_info.size` 에 있습니다.
