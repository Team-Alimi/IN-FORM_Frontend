# 북마크 추가

**공지를 사용자의 북마크에 담습니다. 공지 카드나 상세 화면의 저장 버튼을 켤 때 호출합니다. `POST` 가 아니라 `PUT` 인 이유는 "추가한다" 가 아니라 "이 공지의 북마크 상태를 켬으로 만든다" 이기 때문입니다 — 같은 요청을 몇 번 보내도 결과가 같습니다.**

- **Method / Endpoint: `PUT /api/v1/bookmarks/articles/{articleId}`**
- **Auth Required: Required (User)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |

## Path Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| articleId | Long | 저장할 공지의 ID | **필수** |

> 요청 body 와 쿼리 파라미터는 없습니다. body 를 보내도 무시됩니다.

### 멱등입니다

이미 저장한 공지에 다시 요청해도 `200` 이고, 행이 하나 더 생기지도, 북마크 수가 한 번 더 오르지도 않습니다.
INSERT 를 `ON CONFLICT DO NOTHING` 으로 실행하기 때문입니다.

"있는지 조회하고 없으면 INSERT" 로 짜면 같은 사용자의 요청이 겹칠 때 둘 다 조회를 통과해
한쪽이 PK 위반으로 실패합니다. 더블클릭 한 번에 500 이 나가는 흔한 경로라 그렇게 두지 않았습니다.
**프론트는 연타·재시도·화면 두 개 동시 조작을 따로 방어할 필요가 없습니다.**

### 저장할 수 있는 공지의 범위

요청을 받으면 **먼저 볼 수 있는 공지인지 확인**합니다. 통과 조건은 공지 상세 조회와 같습니다.

| 공지 상태 | 저장 가능 |
| --- | --- |
| `PUBLISHED` | 가능 |
| `PENDING_REVIEW` 이면서 한 번이라도 배포된 적 있음 | 가능 |
| 그 외 (`DRAFT` · `READY_TO_PUBLISH` · 배포 이력 없는 `PENDING_REVIEW` · `TRASHED`) | `404 ARTICLE_NOT_FOUND` |
| 존재하지 않는 ID | `404 ARTICLE_NOT_FOUND` |

> **볼 수 없는 공지와 존재하지 않는 공지가 똑같이 `404` 입니다.** `403` 을 쓰면
> "그 번호의 공지는 존재한다" 는 사실이 새어 나가, 번호를 하나씩 넣어 보는 것만으로
> 미배포 공지의 존재를 알아낼 수 있게 됩니다.

> 재검수로 내려간 공지는 **저장할 수 있습니다.** 상세를 열 수 있으면 저장도 할 수 있어야 하고,
> 북마크 목록에서 열었는데 다시 저장이 막히는 흐름이 되면 안 되기 때문입니다.

## Request Sample

```
PUT /api/v1/bookmarks/articles/42
Authorization: Bearer {access_token}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 항상 `true` |

> **`data` 키가 없습니다.** 이 API 는 본문을 돌려주지 않고(`ApiResponse<Void>`),
> `null` 필드는 응답에서 아예 빠지므로(`default-property-inclusion: non_null`)
> 성공 응답은 **`{"success": true}` 한 줄이 전부**입니다. `error` 키도 없습니다.
>
> **바뀐 `bookmark_count` 는 내려오지 않습니다.** 화면의 저장 수를 갱신하려면
> 로컬에서 낙관적으로 올리거나 목록·상세를 다시 조회해야 합니다.
> (구판 명세에 적힌 `{ "article_id": ..., "bookmarked": true, "bookmark_count": ... }` 는
> 현재 구현과 다릅니다. 코드가 기준입니다.)

## Response Sample

```json
{
  "success": true
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | articleId: 값의 형식이 올바르지 않습니다. | 경로 변수가 정수가 아닌 경우 (`/bookmarks/articles/abc`) |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 404 | ARTICLE_NOT_FOUND | 존재하지 않는 공지입니다. | 없는 ID, 또는 한 번도 배포된 적 없거나 휴지통에 있는 공지 |
| 409 | RESOURCE_BUSY | 요청이 일시적으로 충돌했습니다. 잠시 후 다시 시도해 주세요. | 북마크 수를 갱신하는 트리거가 같은 공지 행에서 경합한 경우. **재시도하면 성공하는 실패**라 5xx 와 구분해 둡니다 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> **이미 저장한 공지를 다시 저장하는 것은 오류가 아닙니다.** `409 DUPLICATE_RESOURCE` 가 나가지 않습니다.
> 저장 버튼의 상태를 서버 응답으로 판정하려 하지 말고, 요청이 200 이면 켜진 것으로 다루면 됩니다.
