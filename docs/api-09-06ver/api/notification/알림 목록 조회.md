# 알림 목록 조회

**로그인한 사용자 본인에게 쌓인 인앱 알림을 최신순으로 조회합니다. 알림함 화면을 열 때, 그리고 무한 스크롤로 다음 페이지를 요청할 때 부릅니다. 알림은 사용자가 만들 수 없는 자원이고 마감 D-1 배치가 만듭니다.**

- **Method / Endpoint: `GET /api/v1/notifications`**
- **Auth Required: Required (User)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |

## Query Param

| Name | Type | Description | Required | Default |
| --- | --- | --- | --- | --- |
| page | Integer | 조회할 페이지 번호 (**1부터 시작**) | 선택 | 1 |
| size | Integer | 페이지당 알림 수. **최대 50** | 선택 | 20 |

> **`sort` 를 보내도 무시됩니다.** 서비스가 받은 `Pageable` 에서 페이지 번호와 크기만 꺼내
> `PageRequest` 를 다시 만들기 때문에 정렬 조건은 그 자리에서 버려집니다.
> 정렬은 쿼리에 `created_at DESC, id DESC` 로 박혀 있습니다. 알림은 최신순 외에 정렬할 이유가 없고,
> 클라이언트가 보낸 정렬을 그대로 받으면 없는 속성 하나에 500 이 나기 때문입니다.
>
> `id DESC` 가 붙어 있는 이유는 마감 알림 배치가 한 트랜잭션에서 수백 건을 만들기 때문입니다.
> PostgreSQL 의 `now()` 는 트랜잭션 시작 시각으로 고정이라 **같은 배치에서 만들어진 알림은 `created_at` 이 전부 같습니다.**
> tie-breaker 가 없으면 페이지 경계에서 같은 알림이 두 번 보이거나 누락됩니다.

> **구판 명세의 `unread_only` 는 없습니다.** 컨트롤러에 그런 파라미터가 없고, 보내도 조용히 버려집니다.
> 안 읽은 개수만 필요하면 안 읽은 개수 조회를 쓰고, 안 읽은 것만 걸러 보여 줄 거라면 클라이언트가 `read` 로 판단해야 합니다.

> `page`·`size` 는 형식이 틀려도 `400` 이 아닙니다. Spring 의 페이징 리졸버가 숫자로 못 읽으면
> 기본값으로 되돌리고, `size` 가 50 을 넘으면 50 으로 잘라 냅니다.

## Request Sample

```
# 알림함 첫 화면
GET /api/v1/notifications

# 다음 페이지
GET /api/v1/notifications?page=2&size=20
```

# Response

### `type` 값

| 값 | 언제 생기나 |
| --- | --- |
| `DEADLINE_D1` | 북마크한 공지의 마감 하루 전. 중복 방지 키가 **마감일**이라 마감이 연장되면 다시 옵니다 |

> **지금 발행되는 종류는 이것 하나뿐입니다.**
>
> DB 에는 `COMMENT_REPLY` 값도 남아 있지만(`ck_notifications_type`) **더 이상 만들어지지 않습니다** —
> 답글 기능이 제거되면서 그 값을 만드는 경로가 사라졌습니다. 이미 쌓인 행이 있으면 목록에 나올 수 있으므로
> 클라이언트는 모르는 `type` 을 만나도 깨지지 않게 기본 렌더링을 두는 편이 안전합니다.

### Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.content | Array | 알림 목록 |
| data.content[].id | Long | 알림 고유 ID. 읽음 처리의 경로 변수로 씁니다 |
| data.content[].type | String | `DEADLINE_D1` \| `COMMENT_REPLY` |
| data.content[].title | String | 알림 제목 (최대 255자) |
| data.content[].message | String | 알림 본문 |
| data.content[].article_id | Long | 눌렀을 때 이동할 공지 ID. **연결된 공지가 없으면 필드 자체가 없습니다** |
| data.content[].read | Boolean | 읽음 여부 |
| data.content[].created_at | String | 생성 일시 (ISO-8601 offset) |
| data.page_info | Object | 페이징 정보 |
| data.page_info.current_page | Integer | 현재 페이지 번호 (1부터) |
| data.page_info.size | Integer | 페이지당 건수 |
| data.page_info.total_pages | Integer | 전체 페이지 수. 0건이면 0 |
| data.page_info.total_items | Long | 전체 건수 |
| data.page_info.has_next | Boolean | 다음 페이지 존재 여부 |
| error | Object | 에러 정보. **성공 응답에는 필드 자체가 없습니다** |

> **필드 이름이 `is_read` 가 아니라 `read` 입니다.** 응답 record 의 컴포넌트 이름이 `read` 라
> 다른 개인화 필드(`is_bookmarked`)와 접두어 규칙이 다릅니다.

> **`article_id` 가 `null` 이면 응답에서 그 키가 사라집니다.** 전역 설정이
> `default-property-inclusion: non_null` 이라 null 필드는 아예 직렬화되지 않습니다.
> 프론트는 `article_id === null` 이 아니라 **키의 존재 여부**로 판단해야 하고,
> 없으면 이동 대상이 없는 알림이므로 탭을 눌러도 아무 데도 가지 않아야 합니다.

> **읽은 시각은 내려가지 않습니다.** DB 에는 `read_at` 이 있지만 응답에는 boolean `read` 만 나갑니다.
> 화면에 쓸 데가 없고, 사용자가 언제 무엇을 읽었는지를 남길 이유가 없다는 판단입니다.

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 이 경로는 사용자 입력을 검증할 것이 없어 `BusinessException` 을 던지지 않습니다.
> 조회 조건이 `WHERE user_id = ?` 하나뿐이라 남의 알림이 섞일 수도, 권한 오류가 날 수도 없습니다.
