# 알림 수신 설정 변경

**마감 알림 메일을 받을지 여부를 켜고 끕니다. 마이페이지의 알림 토글이 이 API 를 부릅니다. 부분 수정이라 보낸 필드만 반영하고, 응답으로는 갱신된 프로필 전체를 돌려줍니다 — 저장 후 `GET /users/me` 를 다시 부를 필요가 없습니다.**

- **Method / Endpoint: `PATCH /api/v1/users/me`**
- **Auth Required: Required (User)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |
| Content-Type | application/json | | **필수** |

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| email_notification_enabled | Boolean | 마감 알림 메일 수신 여부. **보내지 않으면 변경하지 않습니다** | 선택 |

> **본문 자체는 필수입니다.** 필드가 전부 선택이라고 해서 body 를 생략할 수는 없습니다.
> 본문 없이 보내면 `400 MALFORMED_REQUEST` 입니다. 아무것도 안 바꾸려면 `{}` 를 보내세요 —
> 이 경우 오류 없이 현재 프로필이 그대로 내려옵니다(no-op).

> **`null` 은 "끄기" 가 아니라 "건드리지 않기" 입니다.**
> `{"email_notification_enabled": null}` 은 `false` 로 바꾸지 않고 기존 값을 유지합니다.
> 끄려면 반드시 `false` 를 명시적으로 보내야 합니다.

> **이 요청으로 바꿀 수 있는 값은 이것 하나뿐입니다.**
> 이름·이메일은 변경 대상이 아니고(이메일은 계정 식별자), `major_vendor_id` 는 v11 스키마에서
> 제거된 컬럼입니다. 구독 학과는 `PUT /users/me/vendors` 로 다룹니다.
> 정의되지 않은 필드를 함께 보내도 **오류 없이 조용히 무시**되므로, 저장된 줄 알고 넘어가지 않도록
> 응답 값을 확인하세요.

## Request Sample

```json
PATCH /api/v1/users/me
Authorization: Bearer eyJ...
Content-Type: application/json

{
  "email_notification_enabled": false
}
```

아무것도 바꾸지 않는 호출:

```json
PATCH /api/v1/users/me
{}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 갱신된 프로필 전체 (`GET /users/me` 와 같은 모양) |
| data.id | Long | 사용자 고유 ID |
| data.email | String | 로그인 이메일 (항상 소문자) |
| data.name | String | 구글 프로필 이름. **없으면 키 자체가 응답에서 빠집니다** |
| data.role | String | `USER` \| `ADMIN` |
| data.onboarding_completed | Boolean | 온보딩 완료 여부 |
| data.email_notification_enabled | Boolean | 변경 후의 수신 여부 |
| error | Object | 에러 정보 (성공 시 키 자체가 빠짐) |

> **메일 수신을 켜고 끄는 경로는 이것 하나뿐입니다.** 메일 하단의 비로그인 수신거부 링크는
> 두지 않기로 했습니다 — `GET` 이 상태를 바꾸는 구조라 메일 클라이언트나 미리보기 봇이
> 링크를 미리 긁으면 사용자가 누르지도 않았는데 수신이 꺼집니다.
>
> 토글 상태는 로컬에 캐시하지 말고 응답 값을 그대로 반영하세요.

## Response Sample

```json
{
  "success": true,
  "data": {
    "id": 7,
    "email": "kim@inha.ac.kr",
    "name": "김인하",
    "role": "USER",
    "onboarding_completed": true,
    "email_notification_enabled": false
  }
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | 본문이 없거나 JSON 이 아님, `email_notification_enabled` 에 boolean 으로 해석할 수 없는 값을 보냄 |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료·무효화됨 |
| 404 | USER_NOT_FOUND | 존재하지 않는 사용자입니다. | 계정이 없거나 이미 `WITHDRAWN` |
| 409 | CONCURRENT_MODIFICATION | 다른 사용자가 먼저 수정했습니다. 새로고침 후 다시 시도해 주세요. | 저장 중 관리자가 같은 계정의 권한을 바꾼 경우 (낙관적 잠금) |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> **`409` 는 재시도로 해결됩니다.** `users` 행은 본인과 관리자가 동시에 만지는 유일한 테이블이라
> 낙관적 잠금이 걸려 있습니다. 없으면 나중에 커밋한 쪽이 상대의 변경을 조용히 되돌립니다.
> 프론트는 프로필을 다시 읽고 같은 요청을 한 번 더 보내면 됩니다.
>
> 실제로 값을 바꾸지 않은 요청(`{}`, 또는 이미 같은 값)은 행을 갱신하지 않으므로 `409` 가 나지 않습니다.
