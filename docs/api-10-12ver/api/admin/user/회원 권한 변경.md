# 회원 권한 변경

**회원 한 명을 관리자로 승격하거나 일반 회원으로 강등합니다. 관리자 페이지의 회원 목록·상세에서 권한을 바꿀 때 부릅니다. 변경 사실은 "누가 언제 누구를 바꿨는지" 까지 `user_role_logs` 에 자동으로 남습니다 — v1 에서는 DB 를 직접 고치는 것이 유일한 방법이라 그 기록이 아무 데도 없었고, 이 기능의 존재 이유가 바로 그 기록입니다.**

- **Method / Endpoint: `PATCH /api/v1/admin/users/{userId}/role`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 관리자 Access Token | **필수** |
| Content-Type | application/json | | **필수** |

## Path Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| userId | Long | 권한을 바꿀 대상 회원 ID | **필수** |

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| role | String | 바꿀 권한. `USER` \| `ADMIN` | **필수** |

### 거부 규칙 (검사 순서대로)

| 순서 | 조건 | 결과 |
| --- | --- | --- |
| 1 | `{userId}` 가 **요청한 관리자 본인** | `400 CANNOT_CHANGE_OWN_ROLE` |
| 2 | 해당 회원 없음 | `404 USER_NOT_FOUND` |
| 3 | 이미 그 권한임 | `200` — **아무것도 하지 않고** 현재 상태를 돌려줌 |
| 4 | 탈퇴한 회원(`status=WITHDRAWN`)을 `ADMIN` 으로 승격 | `400 INVALID_INPUT_VALUE` |

> **자기 자신의 권한은 바꿀 수 없습니다.** 관리자가 0명이 되는 것을 막는 장치입니다.
> 관리자끼리는 서로를 강등할 수 있지만 자기 자신은 못 하므로, 어떤 순서로 강등해도
> **최소 한 명은 남습니다.** ("관리자 수가 1명이면 거부" 같은 조건으로 세면 두 관리자가
> 동시에 서로를 강등할 때 둘 다 통과해 아무도 안 남습니다.) 관리자가 그만두려면 다른 관리자에게
> 부탁해야 하고, 그 한 단계가 "관리자 0명 → API 로는 복구 불가" 라는 상태를 막습니다.
>
> 검사 순서 1번이라 **자기 자신에게 같은 권한을 보내도 400** 입니다. 3번(무변경 200)까지 가지 않습니다.

> **탈퇴한 회원은 승격만 막고 강등은 허용합니다.** 관리자가 탈퇴하면 계정만 `WITHDRAWN` 이 되고
> `role` 은 `ADMIN` 인 채로 남는데, 그것을 정리할 방법이 없으면 회원 목록에 "탈퇴한 관리자" 가
> 영원히 남기 때문입니다.
>
> 다만 검사 순서상 **이미 `ADMIN` 인 탈퇴 계정에 `ADMIN` 을 다시 보내면 3번에 먼저 걸려 200** 입니다.
> 4번은 실제로 권한이 바뀌는 경우에만 동작합니다.

## Request Sample

```json
PATCH /api/v1/admin/users/7/role
{
  "role": "ADMIN"
}
```

```json
PATCH /api/v1/admin/users/7/role
{
  "role": "USER"
}
```

# Response

성공하면 **변경 후 상태를 다시 읽어** 돌려줍니다. 응답 형태는 회원 목록 한 줄·단건 조회와 같은
`AdminUserSummary` 입니다 — 프론트는 이 응답으로 행을 갱신하면 되고 목록을 다시 부를 필요가 없습니다.

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 변경 후 회원 정보 |
| data.id | Long | 회원 고유 ID |
| data.email | String | 이메일 (**소문자로만 저장**) |
| data.name | String | 이름. 값이 없으면 **필드 자체가 빠집니다** |
| data.role | String | **변경 후** 권한. `USER` \| `ADMIN` |
| data.status | String | `ACTIVE` \| `WITHDRAWN` |
| data.onboarding_completed | Boolean | 온보딩 완료 여부 |
| data.created_at | String | 가입 일시 (ISO-8601 offset) |
| data.withdrawn_at | String | 탈퇴 일시. **활성 회원은 필드 자체가 빠집니다** |

> **응답만 보고는 "실제로 바뀌었는지" 와 "이미 그 권한이었는지" 를 구분할 수 없습니다.**
> 둘 다 200 이고 본문도 같습니다. 구분이 필요하면 요청 전 값과 비교하세요.

> **`null` 필드는 응답에서 아예 빠집니다** (`default-property-inclusion: non_null`).
> 성공 응답에는 `error` 키도, 실패 응답에는 `data` 키도 없습니다.

## 대상자의 세션에 미치는 영향

권한은 Access Token 안에 박혀 있고 요청마다 DB 를 다시 읽지 않습니다. 그래서 **권한이 실제로 바뀐
경우에만** 대상자의 기존 Access Token 을 즉시 무효화합니다. 그러지 않으면 강등된 관리자가
토큰 만료(1시간)까지 관리자 API 를 계속 쓸 수 있고, 그건 권한을 뺏은 것이 아닙니다.

- **로그아웃은 아닙니다.** Refresh Token 은 일부러 남깁니다. 대상자의 클라이언트는 다음 요청에서
  `401 UNAUTHORIZED` 를 한 번 받고 조용히 `POST /api/v1/auth/token/refresh` 로
  **새 권한이 담긴 토큰**을 받으면 됩니다. 재로그인시킬 이유가 없습니다
- **같은 권한을 다시 보낸 요청(위 3번)은 세션을 건드리지 않습니다.** 목록에서 실수로 한 번 더
  누른 것만으로 남이 로그아웃당하면 안 되기 때문입니다
- 강등당한 사람이 관리자 페이지를 열어 두고 있었다면, 그 화면의 모든 `/admin/**` 호출이
  `401` 로 바뀝니다 (`403` 이 아닙니다 — 토큰 자체가 무효화된 것이라서)

> 무효화 처리는 **DB 커밋이 끝난 뒤**에 일어납니다. Redis 는 트랜잭션에 참여하지 않으므로
> 커밋 전에 부르면 이후 롤백 시 "권한은 그대로인데 세션만 끊긴" 상태가 됩니다.

## 감사 기록

권한이 실제로 바뀌면 같은 트랜잭션 안에서 `user_role_logs` 에
`from_role`, `to_role`, `changed_by`(요청한 관리자) 가 한 줄 남습니다. **DB 트리거가 쓰기 때문에
앱이 빠뜨릴 경로 자체가 없습니다.** 같은 권한을 다시 보낸 요청은 이력이 늘어나지 않습니다.

> 이 이력을 조회하는 API 는 **아직 없습니다.** 확인은 DB 에서 합니다.

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | CANNOT_CHANGE_OWN_ROLE | 자신의 권한은 변경할 수 없습니다. 관리자가 한 명도 남지 않는 것을 막기 위한 제한입니다. | `{userId}` 가 요청한 관리자 본인 |
| 400 | INVALID_INPUT_VALUE | 탈퇴한 회원에게는 관리자 권한을 줄 수 없습니다. | 탈퇴 계정을 `ADMIN` 으로 승격 시도 |
| 400 | INVALID_INPUT_VALUE | role: 변경할 권한을 선택해 주세요. | body 에 `role` 이 없거나 `null` |
| 400 | INVALID_INPUT_VALUE | userId: 값의 형식이 올바르지 않습니다. | 경로 변수가 숫자가 아님 |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | body 가 JSON 이 아니거나 **`role` 값이 허용값 밖** (`"SUPER"`, 소문자 `"admin"`) |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | 로그인은 되었으나 `ROLE_ADMIN` 이 아님 |
| 404 | USER_NOT_FOUND | 존재하지 않는 사용자입니다. | 해당 ID 의 회원이 없음 |
| 409 | CONCURRENT_MODIFICATION | 다른 사용자가 먼저 수정했습니다. 새로고침 후 다시 시도해 주세요. | 그 사이 대상자가 탈퇴·설정 변경을 커밋함 (낙관적 잠금) |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> **`role` 오타는 `INVALID_INPUT_VALUE` 가 아니라 `MALFORMED_REQUEST` 입니다.** 값이 enum 으로
> 역직렬화되지 않으면 본문 파싱 단계에서 실패하기 때문에, 필드 자체가 빠진 경우(`INVALID_INPUT_VALUE`)와
> 코드가 갈립니다. 두 코드를 한 덩어리로 처리하면 사용자에게 엉뚱한 안내가 나갑니다.

> **`409` 는 재시도 대상입니다.** 회원 정보는 서로 다른 사람이 동시에 만지는 데이터입니다 —
> 관리자가 권한을 바꾸는 동안 본인이 설정을 바꾸거나 탈퇴합니다. 낙관적 잠금이 없으면 나중에
> 커밋한 쪽이 상대의 변경을 조용히 되돌리고, 그 되돌림까지 감사 로그에
> **"본인이 스스로 강등했다"** 는 없는 사실로 남습니다. 프론트는 이 응답을 받으면 목록을
> 새로고침한 뒤 다시 시도하게 안내하세요.
