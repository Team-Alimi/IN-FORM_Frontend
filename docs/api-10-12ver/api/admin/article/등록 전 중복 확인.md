# 등록 전 중복 확인

**관리자가 공지를 수기로 등록하기 전에 같은 원본이 이미 들어와 있는지 확인합니다. 원본 게시판 글 번호(`external_key`)로 정확히 찾거나, 제목 일부로 찾습니다. 등록 폼에서 번호나 제목을 입력했을 때 "이미 있습니다" 배너를 띄우기 위한 조회입니다.**

- **Method / Endpoint: `GET /api/v1/admin/articles/duplicate-check`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |

## Query Param

| Name | Type | Description | Required | Default |
| --- | --- | --- | --- | --- |
| external_key | String | 원본 게시판 글 번호. **정확 일치** | 선택 | - |
| title | String | 제목 **부분 일치** (대소문자 무시) | 선택 | - |

> **둘 다 비우면 빈 결과입니다.** `{ "exists": false, "articles": [] }` 가 내려오지
> 전체 목록이 나오지 않습니다. 조건 없이 전체를 훑을 이유가 없기 때문입니다.
> 공백만 보낸 것도 안 보낸 것과 같게 처리합니다.
>
> 그래서 **`exists: false` 를 "중복이 없다" 로 읽으면 안 됩니다.** 파라미터를 안 보냈을 때도
> 같은 응답이 나옵니다. 프론트가 조건 없이 호출해 놓고 "중복 없음" 배지를 띄우면 거짓말이 됩니다.

> **두 조건을 함께 주면 `AND` 가 아니라 `OR` 입니다.**
> `?external_key=12345&title=장학금` 은 "번호가 12345 **이거나** 제목에 장학금이 든" 공지를 찾습니다.
> 좁히려고 둘 다 넣으면 오히려 결과가 늘어납니다.

`title` 의 `%` 와 `_` 는 서버가 이스케이프합니다. 앞뒤 공백도 잘라냅니다.

### `external_key` 는 제공처를 가리지 않습니다

`external_key` 는 `article_vendors` 테이블에서 찾는데, **제공처 조건 없이** 값만 봅니다.
그런데 DB 의 유일성 제약은 `(vendor_id, external_key)` 조합입니다 —
즉 같은 번호가 서로 다른 게시판에 각각 존재할 수 있습니다.

> `12345` 같은 흔한 게시글 번호로 찾으면 **전혀 다른 게시판의 공지가 함께 걸립니다.**
> 결과를 "이게 그 공지다" 로 단정하지 말고, 관리자가 제목을 보고 판단하도록 목록을 그대로 보여 주세요.

## Request Sample

```
# 원본 글 번호로 확인
GET /api/v1/admin/articles/duplicate-check?external_key=12345

# 제목 일부로 확인
GET /api/v1/admin/articles/duplicate-check?title=국가장학금

# 둘 다 (OR 로 묶입니다)
GET /api/v1/admin/articles/duplicate-check?external_key=12345&title=국가장학금
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.exists | Boolean | 찾은 공지가 하나라도 있는지. `articles` 가 비어 있지 않은 것과 같습니다 |
| data.articles | Array | 찾은 공지 목록 (ID 내림차순, **최대 20건**) |
| data.articles[].id | Long | 공지 ID |
| data.articles[].title | String | 제목 |
| data.articles[].status | String | 검수 상태 (`PENDING_REVIEW`/`READY_TO_PUBLISH`/`DRAFT`/`PUBLISHED`/`TRASHED`) |
| error | Object | 에러 정보 (성공 시 null) |

`exists` 를 따로 두는 이유는 화면이 목록 길이를 세지 않고 바로 분기하기 위해서입니다.
`exists` 는 원시 타입이고 `articles` 는 빈 배열이라도 배열이므로, **두 필드는 항상 응답에 있습니다.**

> **20건에서 잘립니다. 더 있는지 알 방법이 없습니다.** 총 건수도 `has_next` 도 내려가지 않습니다.
> 흔한 단어로 검색하면 수백 건이 걸리는데 화면은 "이미 있는지" 만 판단하면 되므로 상한을 두었습니다.
> `articles.length === 20` 이면 잘렸을 가능성이 있다고 보고 검색어를 좁히도록 안내하세요.

> **휴지통에 있는 공지도 함께 나옵니다.** 상태 필터를 걸지 않습니다.
> 등록 전 확인이라 "지워진 적 있는 공지" 도 관리자가 알아야 하기 때문인데,
> 화면에서 `status` 를 함께 보여 주지 않으면 관리자가 살아 있는 중복으로 오해합니다.

> **이 결과는 보장이 아닙니다.** 확인 시점과 저장 시점 사이에 다른 관리자가 같은 공지를 넣으면
> 둘 다 "없음" 을 받고 한쪽이 저장에서 실패합니다. 최종 판정은 저장 시점의 DB 제약입니다
> (`(vendor_id, external_key)` 유일 인덱스 → `409 DUPLICATE_RESOURCE`).

## Response Sample

찾은 경우:

```json
{
  "success": true,
  "data": {
    "exists": true,
    "articles": [
      { "id": 42, "title": "2026학년도 1학기 국가장학금 신청 안내", "status": "PENDING_REVIEW" },
      { "id": 39, "title": "[학사] 2026-1학기 국가장학금 2차 신청 안내", "status": "PUBLISHED" },
      { "id": 12, "title": "2025학년도 2학기 국가장학금 안내", "status": "TRASHED" }
    ]
  },
  "error": null
}
```

없거나, 조건을 하나도 주지 않은 경우:

```json
{
  "success": true,
  "data": {
    "exists": false,
    "articles": []
  },
  "error": null
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | `ROLE_ADMIN` 이 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 두 파라미터 모두 문자열이고 필수가 아니라 **검증에 걸릴 것이 없습니다.**
> 빈 값·공백·특수문자 무엇을 보내도 400 이 나지 않고, 조건에 안 맞으면 빈 결과일 뿐입니다.
