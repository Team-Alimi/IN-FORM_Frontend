# 공지 일괄 배포

**검수를 마친 공지들을 한 번에 발행합니다. 검수 목록의 "배포" 버튼과 동아리 공지 발행이 같은 엔드포인트를 씁니다. 내부적으로는 상태를 `PUBLISHED` 로 바꾸는 것이라 상태 일괄 변경과 같은 전이 규칙을 그대로 탑니다.**

- **Method / Endpoint: `POST /api/v1/admin/articles/bulk/publish`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |
| Content-Type | application/json | | **필수** |

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| ids | Array&lt;Long&gt; | 대상 게시글 번호. **1건 이상 200건 이하**. 원소에 `null` 불가 | **필수** |
| memo | String | 상태 이력에 남길 사유. 최대 500자 | 선택 |

> **`memo` 를 받습니다.** 구판 명세 표에는 `bulk/publish` 의 body 가 `ids` 뿐이라고 적혀 있지만
> 실제로는 사유를 함께 받아 상태 이력에 남깁니다.

### 발행할 수 있는 상태는 둘뿐입니다

| 현재 상태 | 결과 |
| --- | --- |
| `READY_TO_PUBLISH` (SCHOOL) | 발행 |
| `DRAFT` (CLUB) | 발행 |
| `PENDING_REVIEW` | **실패** — `INVALID_STATE_TRANSITION` |
| `PUBLISHED` | **실패** — 같은 상태로는 전이하지 않습니다 |
| `TRASHED` | **실패** — 복구 먼저 |

> **검수 대기(`PENDING_REVIEW`)에서 바로 발행할 수 없습니다.** 검수 단계를 건너뛰는 이동이라
> 막습니다. `READY_TO_PUBLISH` 로 먼저 올린 뒤 발행하거나, 재검수 건이라면
> `POST /admin/articles/bulk/review-complete` 를 쓰세요.
>
> **이미 발행된 공지를 다시 선택하면 실패로 돌아옵니다.** 무의미한 전이가 감사 로그를 더럽히지
> 않게 하려는 것입니다. 화면에서 발행 대상만 남겨 보내는 편이 좋습니다.

### `published_at` 은 최초 발행 시각으로 고정입니다

발행 시각은 앱이 아니라 **DB 트리거**가 찍고, **비어 있을 때만** 채웁니다.
배포를 취소했다 다시 올려도 최초 발행 시각이 유지됩니다.

- 앱 시계로 찍으면 인스턴스가 여러 대일 때 발행 순서가 뒤집힙니다
- 크롤러는 정상 공지를 검수 없이 곧바로 `PUBLISHED` 로 직접 INSERT 합니다. 그 경로에도 같은 규칙이 적용되려면 DB 가 채워야 합니다
- `published_at` 이 "한 번이라도 발행된 적 있음" 의 표식이라, 재발행 때마다 갱신하면 재검수 판정도 함께 망가집니다

## Request Sample

```json
POST /api/v1/admin/articles/bulk/publish
{
  "ids": [11, 12, 13],
  "memo": "2월 1주차 정기 배포"
}
```

```json
// 사유 없이
POST /api/v1/admin/articles/bulk/publish
{
  "ids": [512]
}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.succeeded | Array&lt;Long&gt; | 발행에 성공한 게시글 번호 |
| data.failed | Array | 실패한 건 |
| data.failed[].id | Long | 실패한 게시글 번호 |
| data.failed[].code | String | 실패 사유 코드 |
| data.failed[].message | String | 사람이 읽을 사유 |

> **`failed` 가 비어 있지 않아도 HTTP 는 200 입니다.** 프론트는 상태 코드가 아니라
> `failed` 배열을 보고 판단해야 합니다.
>
> 요청한 번호는 **전부** 둘 중 한쪽에 나타납니다. 중복으로 담긴 번호는 한 번으로 합쳐집니다.
> 건별로 트랜잭션이 나뉘므로 한 건이 실패해도 이미 발행된 건은 그대로 남습니다.

### `data.failed[].code` 로 올 수 있는 값

| code | 원인 |
| --- | --- |
| ARTICLE_NOT_FOUND | 그 번호의 공지가 없음 |
| INVALID_STATE_TRANSITION | `PENDING_REVIEW` · `TRASHED` 에서의 발행, 이미 `PUBLISHED` |
| INVALID_INPUT_VALUE | DB CHECK 위반 (23514) |
| CONCURRENT_MODIFICATION | 그 건을 다른 관리자가 먼저 수정 |
| RESOURCE_BUSY | 교착·직렬화 실패. 재시도하면 성공할 수 있습니다 |
| INTERNAL_SERVER_ERROR | 매핑되지 않은 실패 |

## Response Sample

```json
{
  "success": true,
  "data": {
    "succeeded": [11, 12],
    "failed": [
      {
        "id": 13,
        "code": "INVALID_STATE_TRANSITION",
        "message": "허용되지 않은 상태 변경입니다."
      }
    ]
  }
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | ids: 대상 공지를 선택해 주세요. | `ids` 가 비었거나 없음 |
| 400 | INVALID_INPUT_VALUE | ids: 한 번에 200건까지 처리할 수 있습니다. | `ids` 가 200건 초과 |
| 400 | INVALID_INPUT_VALUE | memo: 사유는 500자를 넘을 수 없습니다. | `memo` 500자 초과 |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | JSON 파싱 실패 |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | 관리자가 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 위 표는 **요청 전체가 거부되는 경우**만입니다. 개별 건의 실패는 `data.failed[]` 로 내려갑니다.
