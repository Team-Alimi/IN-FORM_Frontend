# 관리자 공지 목록 조회

**검수 파이프라인에 올라와 있는 공지를 상태·제공처·분류·기간으로 걸러서 봅니다. 관리자 검수 화면의 기본 목록이고, `status=DRAFT` 로 부르면 그대로 동아리 임시저장 목록이 됩니다. 대시보드 카드를 눌렀을 때 넘어오는 목록도 이 엔드포인트입니다.**

- **Method / Endpoint: `GET /api/v1/admin/articles`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |

## Query Param

| Name | Type | Description | Required | Default |
| --- | --- | --- | --- | --- |
| page | Integer | 조회할 페이지 번호 (**1부터 시작**) | 선택 | 1 |
| size | Integer | 페이지당 건수. **상한 50** | 선택 | 20 |
| sort | String | `{필드},{asc\|desc}` 형태. 허용 필드는 아래 표 | 선택 | `created_at,desc` |
| status | List\<String\> | 검수 상태. **복수 지정 가능** (`?status=DRAFT&status=PUBLISHED`). 생략 시 휴지통 제외 전체 | 선택 | - |

### `status` — 생략하면 휴지통을 뺀 전체

파라미터 이름은 **단수 `status` 인데 값은 여러 개**를 받습니다.
`?status=PENDING_REVIEW&status=READY_TO_PUBLISH` 또는 `?status=PENDING_REVIEW,READY_TO_PUBLISH` 둘 다 됩니다.

허용 값은 `PENDING_REVIEW` · `READY_TO_PUBLISH` · `DRAFT` · `PUBLISHED` · `TRASHED` 입니다.
목록에 없는 값을 보내면 `400 INVALID_INPUT_VALUE` 입니다 (enum 이라 **대문자**여야 합니다).

> **생략하면 `status <> 'TRASHED'` 가 걸립니다.** 전체가 아니라 "휴지통을 뺀 전체" 입니다.
> 휴지통은 "지운 것" 이라 기본 화면에 섞이면 관리자가 살아 있는 공지와 구분하지 못합니다.
> 휴지통을 보려면 `status=TRASHED` 를 명시하거나 `GET /admin/articles/trash` 를 쓰세요
> (`previous_status` 가 채워지는 쪽은 후자뿐입니다).

`status` 는 출처 유형과도 묶여 있습니다 — `DRAFT` 는 `CLUB` 에만,
`PENDING_REVIEW` · `READY_TO_PUBLISH` 는 `SCHOOL` 에만 존재합니다(DB CHECK).
`?status=DRAFT&source_type=SCHOOL` 같은 조합은 오류가 아니라 **항상 0건**입니다.

### `sort` 허용 필드

`published_at` · `created_at` · `updated_at` · `ends_on` · `bookmark_count`

목록에 없는 값을 보내면 `400 INVALID_SORT_PROPERTY` 입니다. 정렬 검증은 **건수를 세기 전에** 합니다 —
나중에 하면 결과가 0건일 때 조기 반환되어 검증이 통째로 건너뛰어지고,
같은 잘못된 요청이 데이터 유무에 따라 400 이 되기도 200 이 되기도 합니다.

서버가 **항상 `id desc` 를 뒤에 붙입니다.** 일괄 발행하면 30건의 `published_at` 이 완전히 같아지는데,
tie-breaker 가 없으면 페이지 경계에서 같은 공지가 두 번 나오거나 누락됩니다.
정렬을 명시하면 각 키에 `NULLS LAST` 도 함께 붙습니다 — 마감일 없는 공지가
마감 임박 목록 맨 위에 뜨는 것을 막기 위해서입니다.

> **기본 정렬이 사용자 목록과 다릅니다.** 사용자 목록은 `published_at,desc` 이지만
> 관리자 검수 목록은 **`created_at,desc`** 입니다. 검수는 "새로 들어온 것부터" 보는 화면이고,
> 아직 배포 전이라 `published_at` 이 대부분 비어 있습니다.

> `bookmark_count` 로 정렬할 수는 있지만 **그 값 자체는 응답에 들어 있지 않습니다.**
> 관리자 목록은 카운트를 내려주지 않습니다(아래 Response Param 참고).

### `keyword` — 제목만, 최소 길이 제한 없음

관리자 검색은 **제목만** 봅니다. 사용자 검색(`GET /articles`)과 달리 본문은 보지 않고
pg_bigm 도 쓰지 않습니다 — 관리자는 정확한 제목 조각으로 찾기 때문입니다.

> **`SEARCH_KEYWORD_TOO_SHORT` 가 나지 않습니다.** 사용자 검색은 2글자 미만이면 400 이지만
> 관리자 검색은 `ILIKE` 라 1글자도 그대로 동작합니다. 프론트에서 사용자 검색과 같은
> 최소 길이 검증을 재사용하면 관리자가 한 글자로 찾을 수 있는 경로를 막게 됩니다.

검색어의 `%` 와 `_` 는 서버가 이스케이프합니다. `100%` 를 찾으면 `100` 으로 시작하는 제목이
전부 걸리는 일이 없습니다. 앞뒤 공백은 서버가 잘라냅니다.

### `starts_from` · `ends_to` — 이름과 대상 컬럼이 교차합니다

| 파라미터 | 실제 조건 |
| --- | --- |
| `starts_from` | `ends_on IS NULL OR ends_on >= starts_from` |
| `ends_to` | `starts_on IS NULL OR starts_on <= ends_to` |

> **`starts_from` 이 `starts_on` 을 보지 않습니다.** 두 값을 함께 주면
> "공지 기간이 `[starts_from, ends_to]` 구간과 **겹치는가**" 를 묻는 필터가 됩니다.
> "이 날짜 이후에 시작하는 공지" 로 읽으면 결과를 잘못 해석합니다.
> 기간이 비어 있는(상시) 공지는 `IS NULL` 분기로 **항상 포함**됩니다.

### `needs_review` · `needs_check` — `true` 일 때만 동작합니다

두 값 모두 `Boolean.TRUE.equals(...)` 로 판정합니다.

> **`needs_review=false` 를 보내면 필터가 걸리지 않습니다.** "재검수 아닌 것만" 이 아니라
> "안 보낸 것" 과 똑같이 동작합니다. `needs_check=false` 도 마찬가지입니다.
> 토글을 끄면 파라미터를 아예 빼는 편이 의도와 맞습니다.

`needs_review=true` 의 판정식은 `status = 'PENDING_REVIEW' AND published_at IS NOT NULL` 입니다.
구판 명세의 `review_requested_at` 컬럼은 스키마에서 제거됐습니다 — 재검수 정책이
"노출 유지 + 플래그" 에서 **"검수 대기로 강등"** 으로 바뀌었기 때문입니다.
상태 필터와 독립된 축이라 `?status=PENDING_REVIEW&needs_review=true` 처럼 함께 걸 수 있습니다.

`needs_check=true` 는 아래 여섯 조건 중 **하나라도** 맞으면 걸립니다.

| 조건 | 뜻 |
| --- | --- |
| `similarity_score >= 80` | 중복 의심 (임계값은 설정값 `inform.review.similarity-threshold`) |
| `starts_on IS NULL` | 시작일 누락 |
| `ends_on IS NULL` | 마감일 누락 |
| 정규화 본문 길이 `< 50` | 본문 부실 (임계값은 설정값 `inform.review.min-content-length`) |
| 분류가 하나도 없음 | 분류 미지정 |
| `source_url` 이 있는 제공처가 없음 | 원본 링크 없음 |

> 본문 길이는 HTML 태그를 걷어낸 뒤 잽니다. `<p><br></p>` 만 있어도 원본 길이는 12 라
> 그대로 재면 통과해 버립니다. 제목은 길이 계산에 포함하지 않습니다 —
> 학교 공지 제목은 원래 길어서 제목이 임계값을 미리 갉아먹으면 본문이 비어 있어도 통과합니다.

> `min-content-length` 는 **크롤러 팀과 아직 확정하지 않은 임시값**입니다(Q12).
> 수집 본문의 실제 길이 분포를 봐야 정할 수 있어서, 운영 중에 바뀔 수 있습니다.

## Request Sample

```
# 기본 목록 (1페이지, 20건, 휴지통 제외 전체, 생성 최신순)
GET /api/v1/admin/articles

# 검수 대기 + 발행 대기만
GET /api/v1/admin/articles?status=PENDING_REVIEW&status=READY_TO_PUBLISH

# 임시저장 목록
GET /api/v1/admin/articles?status=DRAFT

# 재검수 대기만 (대시보드 needs_review 카드)
GET /api/v1/admin/articles?needs_review=true

# 확인 필요 목록
GET /api/v1/admin/articles?needs_check=true&page=1&size=20

# 제목 검색 + 제공처 필터 + 수정 최신순
GET /api/v1/admin/articles?keyword=장학금&vendor_id=5&sort=updated_at,desc

# 기간이 2026-02 와 겹치는 공지
GET /api/v1/admin/articles?starts_from=2026-02-01&ends_to=2026-02-28

# 번호로 한 건 찾기
GET /api/v1/admin/articles?article_id=512
```

# Response

### `deadline_status` 분류 기준

| 값 | 조건 |
| --- | --- |
| `UPCOMING` | 오늘 < `starts_on` |
| `OPEN` | 진행 중 |
| `CLOSING_SOON` | `ends_on` 까지 **3일 이내** |
| `CLOSED` | 오늘 > `ends_on` |
| `ALWAYS` | 기간 정보 없음 (상시) |

DB 컬럼이 아니라 **조회 시각에 계산**하는 파생값입니다. 정렬 기준으로 쓸 수 없습니다
(정렬은 `ends_on` 으로 합니다). 검수 상태(`status`)와는 완전히 별개 축입니다 —
v1 에서 두 값이 모두 `status` 라 헷갈렸던 것을 v2 에서 이름으로 갈라 놓았습니다.

> **null 인 필드는 응답에서 사라집니다.** `similarity_score` · `similar_article_id` ·
> `created_by` · `last_status_change` · `starts_on` · `ends_on` · `previous_status` 는
> 값이 없으면 키 자체가 없습니다. `row.created_by === null` 로 판정하지 말고
> `'created_by' in row` 또는 `?? ` 기본값으로 다루세요.

> **`is_bookmarked`·카운트(`bookmark_count`·`comment_count`·`view_count`)가 없습니다.**
> 검수 목록은 "누가 보느냐" 로 달라지는 화면이 아닙니다. 개인화 값을 넣으려면 요청마다
> 관리자 신원을 목록 쿼리에 태워야 하는데, 아무도 쓰지 않는 값 때문에 검수 목록에
> 개인화 축을 만들 이유가 없습니다. 반응 수치는 상세(`GET /admin/articles/{id}`)에서 봅니다.

> **`updated_at` 과 `last_status_change` 는 다른 값입니다.** 앞은 내용이 수정된 시각,
> 뒤는 상태가 바뀐 시각입니다. 검수 화면에서 "언제 손댔는가" 를 보여줄 때는 뒤쪽을 쓰세요.
> AI 요약을 다시 만드는 것은 `updated_at` 을 건드리지 않습니다 —
> 요약 재생성이 "공지가 수정됨" 으로 보이면 안 되기 때문입니다.

> **`vendors` 는 잘리지 않은 전체입니다.** 화면은 보통 3개까지만 보여 주지만 서버는 전부 내려보냅니다 —
> 3개로 잘라 보내면 "더 있는지" 를 클라이언트가 알 수 없습니다. 자르는 것은 클라이언트 몫입니다.

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_SORT_PROPERTY | 허용되지 않은 정렬 기준입니다: {필드} | `sort` 화이트리스트 밖의 필드 |
| 400 | INVALID_INPUT_VALUE | {파라미터명}: 값의 형식이 올바르지 않습니다. | `status`·`source_type` 오타(소문자 포함), 날짜 형식 오류, 숫자 파라미터에 문자 |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | `ROLE_ADMIN` 이 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> **`size` 상한 초과는 오류가 아닙니다.** `size=200` 을 보내면 400 이 아니라 **조용히 50 으로 잘립니다**
> (`spring.data.web.pageable.max-page-size: 50`). 응답의 `page_info.size` 가 실제 적용값이므로,
> 프론트가 요청한 `size` 를 그대로 믿고 페이지를 계산하면 어긋납니다.

> **없는 `vendor_id`·`category_id`·`article_id` 도 오류가 아닙니다.** 존재 검증을 하지 않고
> 조건에 그대로 넣으므로 결과가 0건일 뿐입니다. `VENDOR_NOT_FOUND` 를 기대하지 마세요.
