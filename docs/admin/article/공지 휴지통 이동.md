# 공지 휴지통 이동

**선택한 공지들을 휴지통으로 보냅니다. 목록에서 "삭제" 버튼을 눌렀을 때 실제로 호출되는 것이 이 API 이고, 영구 삭제는 휴지통 화면에서 한 단계 더 거칩니다. 옮기기 직전의 상태가 이력에 남아야 나중에 복구할 곳을 알 수 있습니다.**

- **Method / Endpoint: `POST /api/v1/admin/articles/bulk/trash`**
- **Auth Required: Required (Admin)**

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token | **필수** |
| Content-Type | application/json | | **필수** |

## Body Param

| Name | Type | Description | Required |
| --- | --- | --- | --- |
| ids | Array&lt;Long&gt; | 대상 게시글 번호. **1건 이상 200건 이하**. 원소에 `null` 불가 | **필수** |
| memo | String | 상태 이력에 남길 사유. 최대 500자 | 선택 |

### 어느 상태에서든 갈 수 있습니다 — 이미 휴지통인 것만 빼고

`TRASHED` 로 가는 전이는 모든 상태에서 허용됩니다. 그래서 전이 검사가 사실상 없지만,
**현재 상태를 이력에 남기는 것**이 이 API 의 핵심입니다.

| 현재 상태 | 결과 |
| --- | --- |
| `PENDING_REVIEW` · `READY_TO_PUBLISH` · `DRAFT` · `PUBLISHED` | 휴지통으로 이동 |
| `TRASHED` | **실패** — 같은 상태로는 전이하지 않습니다 (`INVALID_STATE_TRANSITION`) |

> **복구는 이력에 남은 직전 상태로만 갑니다.** 이 요청이 만드는
> `article_status_logs` 한 줄(`from_status` = 옮기기 전 상태, `to_status = TRASHED`)이
> `POST /admin/articles/bulk/restore` 가 참조하는 유일한 단서입니다.
> 앱을 거치지 않고 DB 에서 직접 `TRASHED` 로 바꾼 공지는 **복구할 수 없습니다.**

> **이미 휴지통에 있는 공지를 다시 선택하면 실패로 돌아옵니다.** 화면에서 휴지통 항목을
> 걸러 보내는 편이 좋습니다.

### `memo` 는 DB 트리거가 읽습니다

이력을 기록하는 주체는 앱이 아니라 DB 트리거입니다. 트리거는 "왜" 를 알 수 없어서
앱이 트랜잭션 변수(`app.status_change_memo`)로 넘겨줍니다.

- 안 보내면 오류가 아니라 `memo = NULL` 로 남습니다
- 휴지통 목록(`GET /admin/articles/trash`)과 복구 화면이 이 사유를 그대로 보여 줍니다. "왜 버렸는지" 를 남길 유일한 자리입니다

## Request Sample

```json
POST /api/v1/admin/articles/bulk/trash
{
  "ids": [41, 42],
  "memo": "중복 수집분. 병합 대신 폐기"
}
```

# Response

## Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Object | 응답 데이터 |
| data.succeeded | Array&lt;Long&gt; | 휴지통으로 옮긴 게시글 번호 |
| data.failed | Array | 실패한 건 |
| data.failed[].id | Long | 실패한 게시글 번호 |
| data.failed[].code | String | 실패 사유 코드 |
| data.failed[].message | String | 사람이 읽을 사유 |

> **`failed` 가 비어 있지 않아도 HTTP 는 200 입니다.** 프론트는 상태 코드가 아니라
> `failed` 배열을 보고 판단해야 합니다.
>
> 요청한 번호는 **전부** 둘 중 한쪽에 나타납니다. 중복으로 담긴 번호는 한 번으로 합쳐집니다.
> 건별로 트랜잭션이 나뉘므로 한 건이 실패해도 이미 옮겨진 건은 그대로 남습니다.

### `data.failed[].code` 로 올 수 있는 값

| code | 원인 |
| --- | --- |
| ARTICLE_NOT_FOUND | 그 번호의 공지가 없음 |
| INVALID_STATE_TRANSITION | 이미 `TRASHED` |
| CONCURRENT_MODIFICATION | 그 건을 다른 관리자가 먼저 수정 |
| RESOURCE_BUSY | 교착·직렬화 실패. 재시도하면 성공할 수 있습니다 |
| INVALID_INPUT_VALUE | DB CHECK 위반 (23514) |
| INTERNAL_SERVER_ERROR | 매핑되지 않은 실패 |

## Response Sample

```json
{
  "success": true,
  "data": {
    "succeeded": [41],
    "failed": [
      {
        "id": 42,
        "code": "ARTICLE_NOT_FOUND",
        "message": "존재하지 않는 공지입니다."
      }
    ]
  }
}
```

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | ids: 대상 공지를 선택해 주세요. | `ids` 가 비었거나 없음 |
| 400 | INVALID_INPUT_VALUE | ids: 한 번에 200건까지 처리할 수 있습니다. | `ids` 가 200건 초과 |
| 400 | INVALID_INPUT_VALUE | memo: 사유는 500자를 넘을 수 없습니다. | `memo` 500자 초과 |
| 400 | MALFORMED_REQUEST | 요청 본문을 해석할 수 없습니다. | JSON 파싱 실패 |
| 401 | UNAUTHORIZED | 인증이 필요합니다. | 토큰 없음·만료 |
| 403 | FORBIDDEN | 권한이 없습니다. | 관리자가 아님 |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 위 표는 **요청 전체가 거부되는 경우**만입니다. 개별 건의 실패는 `data.failed[]` 로 내려갑니다.
