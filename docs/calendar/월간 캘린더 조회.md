# 월간 캘린더 조회

**지정한 연·월과 기간이 겹치는 배포 공지를 전부 돌려줍니다. 달력 화면이 한 달치를 통째로 그릴 때 부르는 API 이고, 월을 넘길 때마다 다시 호출합니다. 비로그인도 열리는 유일한 공지 목록이라 서비스를 처음 보는 사람의 첫 화면 역할을 합니다 — 여기서 공지를 눌러 상세로 넘어가면 그때 로그인 벽을 만납니다.**

- **Method / Endpoint: `GET /api/v1/calendar/articles`**
- **Auth Required: Not Required**

> **개인화 필터(`my_major_only`·`interest_only`)를 켤 때만 로그인이 필요합니다.**
> 비로그인으로 그 값을 보내면 `401` 입니다. 구독·관심사가 없는 상태로 통과시키면 빈 목록이 나가는데,
> 그건 "이번 달에 그런 공지가 없다" 와 구분되지 않아 사용자가 로그인이 필요한 줄 모른 채
> 공지가 없다고 믿게 되기 때문입니다.

# Request

## Request Header

| Name | Value | Description | Required |
| --- | --- | --- | --- |
| Authorization | Bearer {access_token} | 서비스 Access Token. 보내면 `is_bookmarked`·`is_liked` 가 본인 기준으로 채워집니다 | 선택 (개인화 필터를 켜면 **필수**) |

> **토큰이 만료·위조되어도 이 경로는 401 이 아니라 200 입니다.** `JwtAuthenticationFilter` 는
> 토큰이 잘못돼도 막지 않고 비로그인으로 통과시킵니다(공개 엔드포인트가 토큰 없이 동작해야 하므로).
> 그래서 만료된 토큰으로 부르면 **조용히 게스트 응답**이 내려오고 `is_bookmarked`·`is_liked` 가
> 전부 `false` 로 보입니다. 달력에서만 북마크가 풀린 것처럼 보이면 토큰 만료를 의심해야 합니다.
> 이때 401 로 만료를 알아채는 경로는 개인화 필터를 켠 요청뿐입니다.

## Query Param

| Name | Type | Description | Required | Default |
| --- | --- | --- | --- | --- |
| year | Integer | 조회할 연도. **2000~2100** | **필수** | - |
| month | Integer | 조회할 월. **1~12** | **필수** | - |
| category_id | List | 분류 ID 다중 필터 (예: `1,2` 또는 `category_id=1&category_id=2`) | 선택 | - |
| my_major_only | Boolean | 구독한 학과·기관의 공지만 (**로그인 필요**) | 선택 | false |
| interest_only | Boolean | 온보딩에서 고른 관심 카테고리의 공지만 (**로그인 필요**) | 선택 | false |

### 개인화 필터 두 가지

둘은 **다른 축**이라 함께 켜면 AND 로 걸립니다 — "내가 구독한 학과의, 내 관심 카테고리 공지".

| | 보는 것 |
| --- | --- |
| `my_major_only` | 구독한 학과·기관 (`user_vendors`) |
| `interest_only` | 관심 카테고리 (`user_interest_categories`) |

> **`interest_only` 는 공지 목록(`GET /articles`)의 같은 이름 파라미터와 동작이 완전히 같습니다.**
> 기본 꺼짐이고, 폴백이 없어서 **관심 카테고리가 0개인 사용자가 `true` 로 부르면 빈 달력**이
> 정상 200 으로 내려갑니다. 두 화면이 같은 토글을 다르게 해석하면 사용자가 필터를 믿을 수 없어서
> 일부러 맞춰 두었습니다.

### `year`·`month` 검증

`CalendarQuery` 생성자가 직접 검사합니다. 범위를 벗어나면 `400 INVALID_INPUT_VALUE` 이고
메시지는 각각 `"연도는 2000~2100 사이여야 합니다."`, `"월은 1~12 사이여야 합니다."` 입니다.

> 검증을 앱에서 하는 이유가 있습니다. `month=13` 을 그대로 `LocalDate` 에 넘기면 `DateTimeException`
> 이 나는데 그건 SQLSTATE 가 없어 `GlobalExceptionHandler` 의 마지막 그물에 걸려 **500** 으로 나갑니다.
> 잘못된 입력이 5xx 로 나가면 프론트가 재시도 대상으로 다뤄 고쳐질 리 없는 요청을 무한 재시도합니다.
> 연도 상한도 같은 이유입니다 — `year=999999999` 는 날짜 계산이 오버플로로 터집니다.

### `category_id` 주의

**존재하지 않는 분류 ID 를 보내도 에러가 아닙니다.** 그런 ID 가 붙은 공지가 없으니 조용히 빈 배열이
내려옵니다. `CATEGORY_NOT_FOUND` 는 이 경로에서 나오지 않습니다. 분류 목록은 `GET /categories` 로
받아 그 안의 ID 만 쓰세요.

### `my_major_only` 판정 기준

구독 정보(`user_vendors`)에 담긴 제공처가 붙은 공지만 남깁니다. 그 테이블은 트리거가 `SCHOOL` 유형만
허용하므로 사실상 **학과·기관 구독**입니다. 제공처가 하나도 붙지 않은 공지는 이 필터에서 빠집니다.

## Request Sample

```
# 2026년 5월 달력 (비로그인 가능)
GET /api/v1/calendar/articles?year=2026&month=5

# 분류 다중 필터
GET /api/v1/calendar/articles?year=2026&month=5&category_id=1,3

# 내 학과만 (Authorization 헤더 필수)
GET /api/v1/calendar/articles?year=2026&month=5&my_major_only=true
```

# Response

### 어떤 공지가 나오는가

| 조건 | 포함 여부 |
| --- | --- |
| `starts_on`~`ends_on` 이 그 달과 하루라도 겹침 | 포함 |
| 시작·끝이 모두 그 달 밖이지만 달을 통째로 걸침 (4월 시작 ~ 6월 마감) | 포함 |
| `starts_on` 만 있음 (마감 없는 상시) | 포함 — 없는 쪽을 무한으로 봅니다 |
| `ends_on` 만 있음 ("상시 모집, 5월 말 마감") | 포함 — 같은 이유 |
| **`starts_on`·`ends_on` 이 둘 다 없음** | **제외** |
| 상태가 `PUBLISHED` 가 아님 (미배포·재검수 대기·휴지통) | 제외 |

> **날짜가 하나도 없는 공지는 나오지 않습니다.** 달력은 날짜 위에 올리는 화면이라 놓을 자리가 없습니다.
> 목록 화면(`GET /articles`)에는 나오는 공지가 달력에는 없는 것이 정상입니다.
>
> 노출 기준이 `PUBLISHED` **단일**이라는 점도 중요합니다. 상세·북마크 목록은 재검수로 내려간 공지까지
> 보여 주지만(`under_review`), 달력은 비로그인에게 열려 있어 기준을 좁게 잡았습니다.
> 그래서 이 응답의 `under_review` 는 **항상 `false`** 입니다.

### 정렬과 상한

- 정렬은 **`starts_on` 오름차순**입니다. `starts_on` 이 없으면 `ends_on` 을 대신 쓰고, 같으면 `id` 오름차순입니다.
  발행일 역순인 목록 화면과 다릅니다.
- **페이징이 없습니다.** `page`·`size` 를 보내도 무시되고, 응답에 `page_info` 나 `content` 도 없습니다.
  `data` 가 배열 그 자체입니다.
- 대신 **최대 300건**의 안전 상한이 있습니다.

> **상한에 걸려 잘려도 응답으로는 알 수 없습니다.** 서버는 경고 로그만 남기고 300건을 그대로 200 으로
> 돌려줍니다. 잘렸다는 표시가 응답에 없으므로, 프론트는 "그달에 원래 300건뿐" 인 것과 구별할 수 없습니다.
> 실제 한 달 배포량(수십 건)보다 넉넉한 값이라 정상 운영에서는 닿지 않습니다.

### `deadline_status` 분류 기준

| 값 | 조건 |
| --- | --- |
| `UPCOMING` | 오늘 < `starts_on` |
| `OPEN` | 진행 중 (시작만 있고 마감이 없는 경우 포함) |
| `CLOSING_SOON` | `ends_on` 까지 **3일 이내** |
| `CLOSED` | 오늘 > `ends_on` |
| `ALWAYS` | 기간 정보 없음 (상시) |

> DB 컬럼이 아니라 **조회 시각에 계산**하는 파생값입니다. 한 응답 안의 모든 항목은 같은 기준일로 판정합니다.
>
> **이 엔드포인트에서는 `ALWAYS` 가 절대 나오지 않습니다.** 날짜가 둘 다 없는 공지를 애초에 제외하기 때문입니다.
> 반대로 `CLOSED` 는 나옵니다 — 이번 달 안에 이미 마감된 공지도 달력에는 그려야 하기 때문입니다.

### Response Param

| name | type | 비고 |
| --- | --- | --- |
| success | Boolean | 요청 성공 여부 |
| data | Array | 공지 목록. **배열 그 자체입니다** (`content`·`page_info` 없음) |
| data[].id | Long | 게시글 고유 ID |
| data[].source_type | String | `SCHOOL` \| `CLUB` |
| data[].title | String | 제목 |
| data[].summary | String | AI 생성 요약. **미생성이면 필드 자체가 없습니다** |
| data[].published_at | String | 발행 일시 (ISO-8601 offset) |
| data[].starts_on | String | 시작일 (yyyy-MM-dd). **없으면 필드 자체가 없습니다** |
| data[].ends_on | String | 마감일 (yyyy-MM-dd). **없으면 필드 자체가 없습니다** |
| data[].deadline_status | String | 마감 상태 (위 표). `ALWAYS` 는 나오지 않음 |
| data[].bookmark_count | Integer | 전체 북마크 수 |
| data[].like_count | Integer | 전체 좋아요 수 |
| data[].comment_count | Integer | 댓글 수 (삭제 자리는 제외) |
| data[].view_count | Long | 조회 수 |
| data[].is_bookmarked | Boolean | 본인 북마크 여부. **비로그인이면 항상 false** |
| data[].is_liked | Boolean | 본인 좋아요 여부. **비로그인이면 항상 false** |
| data[].has_attachment | Boolean | 첨부 존재 여부 (클립 아이콘용). 개수·목록은 상세에서 |
| data[].under_review | Boolean | 재검수 배지. **이 API 에서는 항상 false** |
| data[].vendors | Array | 제공처 목록. 없으면 `[]` |
| data[].vendors[].id | Long | 제공처 ID |
| data[].vendors[].name | String | 제공처 이름 |
| data[].vendors[].initial | String | 축약 표시 (좁은 칸용, 예: "컴공") |
| data[].vendors[].type | String | `SCHOOL` \| `CLUB` |
| data[].categories | Array | 분류 목록. 없으면 `[]` |
| data[].categories[].id | Long | 분류 ID |
| data[].categories[].name | String | 분류 이름 |
| error | Object | 실패 시에만 존재 |

> **null 필드는 응답에서 아예 빠집니다**(`default-property-inclusion: non_null`).
> `summary`·`starts_on`·`ends_on` 은 값이 없으면 키 자체가 사라지므로 `row.starts_on` 이 항상 있다고
> 가정하면 안 됩니다. 같은 이유로 **성공 응답에는 `error` 키가 없고, 실패 응답에는 `data` 키가 없습니다.**
>
> 단, `starts_on`·`ends_on` 이 **동시에** 사라지는 일은 이 API 에서는 없습니다. 달력이 그런 공지를
> 아예 제외하기 때문에 최소 한쪽은 항상 들어 있습니다 — 그것을 달력 칸의 배치 기준으로 쓸 수 있습니다.
>
> `vendors`·`categories` 는 **배열**입니다. 같은 공지가 학과 게시판과 교무처 게시판에 동시에 올라오는
> 일이 흔하고, 분류도 여러 개가 붙습니다. 같은 게시판에 재게시된 원본이 여러 행으로 남아 있어도
> 제공처 칩은 한 번만 나갑니다.

# Error

| HTTP Status | Code | Message | Description |
| --- | --- | --- | --- |
| 400 | INVALID_INPUT_VALUE | 연도는 2000~2100 사이여야 합니다. | `year` 가 범위 밖 |
| 400 | INVALID_INPUT_VALUE | 월은 1~12 사이여야 합니다. | `month` 가 범위 밖 |
| 400 | INVALID_INPUT_VALUE | year: 필수 파라미터입니다. | `year`·`month` 를 아예 보내지 않음 (파라미터 이름이 메시지 앞에 붙습니다) |
| 400 | INVALID_INPUT_VALUE | year: 값의 형식이 올바르지 않습니다. | 숫자가 아닌 `year`·`month`·`category_id`, boolean 으로 해석할 수 없는 `my_major_only` |
| 401 | UNAUTHORIZED | 내 학과 공지만 보려면 로그인이 필요합니다. | 비로그인(또는 만료 토큰) 상태로 `my_major_only=true` |
| 500 | INTERNAL_SERVER_ERROR | 서버 내부 오류가 발생했습니다. | 서버 측 처리 오류 |

> 401 의 메시지는 공통 `"인증이 필요합니다."` 가 아니라 **`"내 학과 공지만 보려면 로그인이 필요합니다."`**
> 입니다. 다른 화면에서 오는 401(토큰 만료)과 달리 "달력은 계속 볼 수 있고 이 토글만 로그인이 필요하다"
> 는 뜻이므로, 화면을 통째로 로그인 페이지로 보내지 말고 토글만 되돌리는 편이 맞습니다.
>
> 이 경로에서는 `RESOURCE_NOT_FOUND`·`CATEGORY_NOT_FOUND` 가 나오지 않습니다. 조회 전용이고
> 조건에 맞는 공지가 없으면 **빈 배열과 200** 입니다.
